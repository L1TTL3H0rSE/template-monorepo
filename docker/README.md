# Docker

## Запуск

```bash
docker compose --parallel 4 up -d --build
docker compose --parallel 4 down
```

`--parallel` указывается **всегда**: без него образы собираются
последовательно.

| Сервис | Адрес |
|---|---|
| `web` | http://localhost:3000 |
| `gotemplate` | http://localhost:8080 |
| `postgres` | localhost:5432 |

Перед сервисом выполняется одноразовый `gotemplate-bootstrap` — засев корневых
данных. Сервис поднимается только при `service_completed_successfully`:
работать на наполовину заполненной БД он не должен. Разбор —
[`docs/backend/bootstrap-data.md`](../docs/backend/bootstrap-data.md).

Только инфраструктура, без приложений:

```bash
docker compose --parallel 4 up -d postgres
```

Это рабочий режим разработки: БД в контейнере, сервис и фронтенд — локально, с
горячей перезагрузкой.

## Образы

| Файл | Собирает |
|---|---|
| `Dockerfile.service` | Один Go-сервис; какой — задаёт `SERVICE_DIR` |
| `Dockerfile.frontend` | Nuxt-приложение вместе с пакетами workspace |

Оба берут контекстом **корень репозитория**: Go-сервис зависит от
`backend/kit` через `replace`, а приложение — от пакетов workspace.

## Решения в `Dockerfile.service`

**Общие модули копируются до развилки по `SERVICE_DIR`.** Слой скачивания
зависимостей одинаков для всех сервисов и хранится однократно. Если поставить
его после развилки, каждый образ получит свою копию.

**`ARG SERVICE_DIR` объявлен после этого слоя.** BuildKit включает значения
объявленных build-args в cache key каждого последующего `RUN`. Объявление в
начале стадии дало бы отдельный слой зависимостей на каждый сервис.

**`GOPROXY=off` при сборке.** Делает промах кеша модулей видимым: иначе
недостающий модуль молча докачивается в per-service слой — ровно то
дублирование, которое общий слой и убирает.

## Решения в `Dockerfile.frontend`

**Манифесты копируются отдельно от исходников.** Слой установки зависимостей
инвалидируется при изменении `package.json`, а не при каждой правке кода.

**`pnpm build:local` перед сборкой приложения.** Пакеты экспортируют `dist`;
без этого шага приложение соберётся с пустыми модулями.

**Финальный образ содержит только `.output`.** Nitro собирает самодостаточный
бандл — `node_modules` в рантайме не нужны.

## Пределы, которые кончаются раньше всего

### Соединения PostgreSQL

Дефолт Postgres — 100 соединений. Каждый Go-сервис держит **свой** пул
(`DB_MAX_CONNS`, по умолчанию 10). Пятнадцать сервисов — это 150 соединений в
покое, плюс миграции при старте, плюс `psql` разработчика.

Стенд падает с `FATAL: sorry, too many clients already`, причём падает не тот
сервис, который исчерпал лимит, а тот, который подключился последним. Симптом
выглядит как случайные `500` в произвольном месте.

```yaml
command: [postgres, -c, max_connections=500, -c, shared_buffers=256MB]
```

Правило: `max_connections >= сумма DB_MAX_CONNS всех сервисов + 50`.

Каждое соединение стоит памяти, поэтому в production ответ другой — pgbouncer в
режиме transaction pooling, а не дальнейший рост этого числа.

### Права на артефакты (EACCES)

Если хостовый `dist`/`.nuxt` попадает в контекст сборки, а потом монтируется
обратно, каталог оказывается создан root'ом внутри контейнера. Локальный
`pnpm build` после этого падает с `EACCES`, и починить это можно только
`sudo rm -rf`.

Два правила: артефакты перечислены в `.dockerignore`, финальные образы работают
от непривилегированного пользователя.

### UDP-порты для медиа

Если в стек добавляется WebRTC-сервис (LiveKit, mediasoup), его пул UDP-портов
для dev-окружения **обязательно ограничивается**:

```yaml
ports:
  - "50000-50019:50000-50019/udp"
```

Стандартный пул в сотни портов убивает docker-proxy: он поднимает по процессу
на порт. Симптом — контейнер не стартует, а хост уходит в своп. В production
такой сервис работает через `network_mode: host`, а не через проброс портов.

### Память при сборке

Одновременная сборка десятка образов с включённым Go build cache и pnpm store
выедает память. `--parallel 4` — не только про скорость: это ещё и потолок
одновременных сборок.

## Общее

- Оба финальных образа работают от непривилегированного пользователя.
- Cache-mount для модулей и build-кеша переживает инвалидацию слоёв: пересборка
  после правки исходников не ходит в сеть.
- Healthcheck у `postgres` обязателен: сервис зависит от готовности БД, а не от
  факта запуска контейнера.
- `Dockerfile.service` собирает **все** команды из `cmd/*`, поэтому одноразовый
  `bootstrap` едет в том же образе, что и сервис.

## Добавление сервиса

1. Строка `COPY backend/go<домен> /src/go<домен>` в `Dockerfile.service`, рядом
   с остальными — **до** развилки по `SERVICE_DIR`.
2. Запись в `docker-compose.yml` с `args: SERVICE_DIR: go<домен>`.
3. Переменные окружения по образцу `gotemplate`.

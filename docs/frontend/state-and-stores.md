# Состояние и сторы

## Что где хранить

| Состояние | Где | Почему |
|---|---|---|
| Открыт ли дропдаун | `ref` в компоненте | Никому больше не нужно |
| Черновик формы | Композабл экрана | Должен исчезнуть вместе с экраном |
| Список с фильтром и страницей | Стор | Переживает переход и возврат |
| Профиль текущего пользователя | Стор | Нужен всему приложению |
| Данные для одной карточки | `useAsyncState` в компоненте | Живут столько же, сколько карточка |

Ошибка в обе стороны заметна не сразу:

- **форма в глобальном сторе** показывает недописанный текст при следующем
  открытии;
- **список в локальном состоянии** перезагружается при каждом возврате на
  страницу и теряет позицию скролла и выбранный фильтр.

## Setup-форма стора

```ts
export const useCharactersStore = defineStore("characters", () => {
  const api = useApi();

  const items = ref<Character[]>([]);
  const pending = ref(false);
  const error = ref<string | null>(null);

  const pagination = usePagination(12);
  const search = useSearchQuery({ minLength: 2 });

  async function load() { /* ... */ }

  return { items, pending, error, pagination, search, load };
});
```

Setup-форма, а не options: она пишется тем же кодом, что и композабл, и
позволяет использовать общие композаблы `@starter/shared` прямо внутри стора.
В options-форме `usePagination()` вызвать негде.

## Ловушка: `reactive` разворачивает вложенные ref-ы

Pinia оборачивает результат setup-стора в `reactive()`, который разворачивает
ref-ы **и во вложенных объектах**:

```vue
<!-- ✘ вернёт undefined -->
<nav v-if="store.pagination.totalPages.value > 1">

<!-- ✔ -->
<nav v-if="store.pagination.totalPages > 1">
```

Это ловит `nuxt typecheck` — но только если он входит в обязательные проверки.
Без него ошибка проявляется как «пагинация никогда не показывается».

## Три состояния списка

Загрузка, ошибка и пусто описываются явно:

```vue
<p v-if="store.pending">Загружаем…</p>
<p v-else-if="store.error" role="alert">{{ store.error }}</p>
<p v-else-if="!store.items.length">Ничего не найдено.</p>
<div v-else>…</div>
```

Шаблон, в котором есть только `v-for`, показывает пустой экран и при загрузке, и
при сбое сети. Пользователь не может их различить и просто уходит.

`role="alert"` на сообщении об ошибке: иначе пользователь скринридера не узнает,
что что-то пошло не так.

## Реакция на изменение параметров: ровно одно чтение

```ts
watch(search.applied, () => {
  if (pagination.page.value === 1) {
    void load();
    return;
  }

  // Сброс страницы разбудит наблюдателя ниже, и чтение выполнит он.
  pagination.reset();
});
watch(pagination.page, () => void load());
```

Здесь два требования, и наивная реализация выполняет только первое.

**Сброс страницы обязателен.** Без него пользователь ищет, находясь на
странице 5, и попадает на страницу 5 новой выдачи — то есть на пустой экран.

**Но чтение должен выполнять ровно один владелец.** Очевидная пара

```ts
// ✘ два чтения, если пользователь не на первой странице
watch(search.applied, () => {
  pagination.reset();
  void load();
});
```

даёт **два** запроса: сброс страницы будит наблюдателя за `pagination.page`, и
тот запускает своё чтение. Второй запрос уходит с теми же параметрами и
гарантированно отменяет первый, поэтому в devtools при каждом поиске виден
отменённый запрос.

Условная схема выше передаёт ответственность одному наблюдателю: если страница
уже первая, сброс ничего не разбудит и читает сам обработчик поиска; иначе
читает наблюдатель за страницей.

## Latest-request-wins

Интерактивное чтение с меняющимися параметрами обязано гарантировать, что
устаревший ответ не перезапишет более новое состояние.

```ts
let loadGeneration = 0;
let loadController: AbortController | undefined;

async function load(): Promise<void> {
  const generation = ++loadGeneration;

  loadController?.abort();
  const controller = new AbortController();
  loadController = controller;

  pending.value = true;
  error.value = null;

  try {
    const page = await api.characters.search(
      { /* ... */ },
      { signal: controller.signal },
    );

    if (generation !== loadGeneration) return;

    serverItems.value = page.items;
    pagination.setTotal(page.total);
  } catch (caught) {
    if (generation !== loadGeneration) return;
    if (isCancelled(caught) || controller.signal.aborted) return;

    error.value = /* сообщение пользователю */;
    serverItems.value = [];
  } finally {
    if (generation === loadGeneration) pending.value = false;
  }
}
```

### Почему нужны и отмена, и счётчик

В этой ручной схеме они решают разные задачи. Если готовый контроллер уже
обеспечивает нужные гарантии, используй его вместо дополнительного механизма.

| Механизм | Что даёт | Чего не может |
|---|---|---|
| `AbortController` | Прерывает поддерживающую отмену работу | Не отзывает уже полученный результат и не гарантирует остановку сервера |
| Счётчик поколений | Гарантирует, что записать может только актуальное чтение | Не экономит сеть |

Если ответ успел прийти до `abort()` — или транспорт отмену не поддерживает —
устаревшее чтение всё равно попытается записать состояние. Счётчик это
закрывает.

Счётчик охраняет **три** вещи, а не только данные: `serverItems`, `error` и
снятие `pending`. Последнее легко забыть, и тогда отменённый запрос гасит
индикатор загрузки, которая всё ещё идёт.

### Отмена — не ошибка

```ts
if (isCancelled(caught) || controller.signal.aborted) return;
```

Отменённое чтение молчит. Показать его как ошибку означает мигать «Сервис
недоступен» при обычном наборе текста в поиске: каждый новый применённый
запрос отменяет предыдущий.

Транспорт различает эти случаи отдельным типом `RequestCancelledError` —
см. [`api-and-adapters.md`](api-and-adapters.md).

### Уход со страницы

```ts
onScopeDispose(() => {
  loadGeneration += 1;
  loadController?.abort();
});
```

Это требование к lifecycle владельца, а не утверждение, что каждый helper
уже его реализует. Поколение запрещает запись даже если транспорт игнорирует
abort. При reset того же живого владельца также инвалидируй поколение,
отмени чтение и явно установи новое data/error/pending по контракту reset.
У Pinia-стора уход компонента не равен dispose стора: если данные нужны другим
читателям, их общую операцию нельзя отменять вместе с одним представлением.

## Черновик и повтор сохранения

Редактор владеет draft и lifecycle формы; общий стор — подтверждёнными данными.
Сохраняй независимый submitted-снимок до запроса. Если после отправки A
пользователь ввёл B, успех A обновляет baseline подтверждённым ответом,
но не заменяет B и не сбрасывает dirty без сравнения. Нормализация сервера
требует явного правила применения; универсальный merge не предполагается.

Повтор сохранения обычно пропускается до завершения текущего — проверка нужна
у владельца, а не только в кнопке. Очередь команд или параллельные сохранения
требуют отдельного порядка подтверждений. Замещение чтения не переносится
автоматически на запись: abort не откатывает выполненную сервером мутацию.

Для сложных взаимоисключающих фаз формы используй discriminated union.
Независимые флаги выбора и раскрытия остаются отдельными. Конфликт двух
пользователей требует атомарной проверки версии сервером; локальное поколение
решает другую задачу. При отсутствии такого API ограничение фиксируется,
а изменение backend согласуется отдельно.

## Ошибки в сторе

Стор превращает ошибку в **текст для пользователя**, а не пробрасывает объект в
шаблон:

```ts
catch (caught) {
  error.value = caught instanceof Error
    ? caught.message
    : "Не удалось загрузить список";
  items.value = [];
}
```

`items.value = []` обязателен: иначе поверх сообщения об ошибке остаётся старая
выдача, и пользователь считает её актуальной.

## Границы стора

Стор владеет состоянием **списка**, а не отдельной сущности. Форма
редактирования живёт в композабле экрана.

Стор **не знает** про HTTP: он вызывает `api.characters.search(...)`, где `api`
— порт из [`api-and-adapters.md`](api-and-adapters.md). Благодаря этому стор
одинаково работает с mock- и http-провайдером.

## Именование

```ts
defineStore("characters", ...)          // ✔ домен
defineStore("components/modals", ...)   // ✔ пространство пакета
defineStore("data", ...)                // ✘ ни о чём
```

Идентификатор стора виден в devtools и в персистентном хранилище — он должен
что-то значить.

## `markRaw` для компонентов в состоянии

```ts
entries.set(key, { component: markRaw(options.component) });
```

Компонент — не реактивные данные. Без `markRaw` Vue оборачивает его определение
в прокси и выдаёт предупреждение, а в отдельных случаях ломает рендер.

`shallowReactive` для карты записей: реактивна сама карта (добавление и
удаление), а props остаются непрозрачными значениями. Глубокая реактивность
здесь только замедляет.

# Тестирование фронтенда

## Ложное покрытие `.vue` — главная ловушка

Провайдер покрытия `v8` считает покрытие по инструментированному выводу, а не по
исходнику. Для `.vue` это означает: файл, который просто **импортировали**, но ни
разу не отрендерили, показывает **100% покрытия**.

Метрика при этом не просто завышена — она обратна смыслу: чем больше
компонентов подтягивает барель, тем «лучше» выглядит покрытие.

### Что лечит

Лечит это AST-aware remapping: отчёт становится честным, и неотрендеренный
компонент показывает 0%.

В vitest 3 его включали явно — `coverage.experimentalAstAwareRemapping: true`.
С vitest 4 опция удалена, потому что remapping включён всегда:

```ts
coverage: {
  provider: "v8",
}
```

Проверить, что он работает, можно за минуту: импортируйте компонент в тесте, не
монтируя его, и посмотрите отчёт. 100% — remapping не действует.

### Чего не делать

Не подгонять порог под цифру. Если покрытие упало после включения remapping —
оно и было таким, просто это не было видно.

## Разделение по окружениям

```text
test/unit/**    Node-окружение: контракты, адаптеры, композаблы, чистая логика
test/nuxt/**    окружение Nuxt (@nuxt/test-utils, mountSuspended)
```

Разделение обязательно, а не для порядка: Node-окружение **не видит**
`app/pages/**` и `app/layouts/**` — там нужны авто-импорты, роутер и runtime
config. Оставленные в подсчёте покрытия, эти каталоги дают ноль и обесценивают
общую цифру.

Поэтому в `vitest.config.ts` приложения они исключены из `coverage.include`, а
покрывать их следует тестами из `test/nuxt`, а не расширением исключений.

## Что тестировать

| Слой | Что проверяем | Чем |
|---|---|---|
| Композабл | Гонки, снятие таймеров, границы | Обычный вызов, `effectScope` при hooks |
| Транспорт | Разбор конверта, типы ошибок, заголовки | Подмена `fetch` через `vi.stubGlobal` |
| Адаптер / порт | Контракт, одинаковый для http и mock | Тест на **порт**, а не на реализацию |
| Компонент | Контракт разметки и доступности | `mount` из `@vue/test-utils` |
| Стор | Реакция на смену параметров, состояния списка | Прямой вызов действий |

### Тест на порт, а не на реализацию

```ts
describe("CharacterApi (mock)", () => {
  it("возвращает страницу и общее количество", async () => {
    const page = await api.search({ limit: 2, offset: 0 });

    expect(page.items).toHaveLength(2);
    expect(page.total).toBe(3);   // total — всего подходящих, а не длина страницы
  });
});
```

Тот же набор проверок применим к HTTP-адаптеру. Расхождение реализаций — самая
дорогая ошибка схемы «порт + адаптеры», потому что проявляется только в проде.

### Тест компонента проверяет контракт, а не пиксели

```ts
it("переносит модификаторы в атрибуты", () => {
  const wrapper = mount(Button, { props: { variant: "outlined" } });

  expect(wrapper.attributes("variant")).toBe("outlined");
});
```

Проверяется то, на что опирается вся система стилей. Если модификатор перестанет
попадать в атрибут, селекторы `[variant="..."]` замолчат — CSS не умеет
сообщать, что не нашёл элемент.

Скриншотные сравнения в этот набор не входят: они ломаются от смены шрифта и
версии браузера чаще, чем ловят регрессии.

## Ловушка утверждений, которые всегда истинны

```ts
// Проходит и когда всё сломано: undefined === undefined
expect(wrapper.attributes("is-loading")).toBeUndefined();
```

Такое утверждение обязано быть **парным**: рядом должен быть тест, который
проверяет наличие того же атрибута во включённом состоянии. Иначе он молча
перестаёт что-либо проверять.

Ровно так в этом шаблоне обнаружился реальный дефект: ведущий HTML-комментарий в
`<template>` делал компонент multi-root, атрибуты не попадали на корневой
элемент, а «отрицательный» тест продолжал проходить.

## Guard-тесты

Два теста в `packages/components/test` не проверяют поведение, а охраняют
инварианты:

| Тест | Что охраняет |
|---|---|
| `public-surface.test.ts` | Публичная поверхность равна reviewed allowlist |
| `template-root.test.ts` | `<template>` не начинается с комментария |

Оба ловят то, что не ловится ни компилятором, ни ревью в списке из полусотни
файлов.

## Команды

```bash
pnpm test            # весь workspace
pnpm test:coverage   # с отчётом покрытия
pnpm --filter @starter/shared test
pnpm vitest -t "название теста"
```

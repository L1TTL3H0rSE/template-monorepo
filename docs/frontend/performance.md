# Производительность фронтенда

## 1. Цель и рабочий цикл

Производительность оценивается по **реальным пользовательским сценариям**, а не
по ощущению от кода.

```text
проблема пользователя
  -> baseline
  -> bottleneck через профиль
  -> гипотеза
  -> минимальное изменение
  -> повторное измерение
  -> проверка функциональной регрессии
```

Правило: **не заявлять «стало быстрее» там, где это можно измерить, но не
измерено.** Код, который выглядит теоретически быстрее, регулярно оказывается
медленнее — а иногда просто выполняется реже, чем казалось.

Главная модель стоимости — конвейер, по которому проходит работа:

```text
сеть -> доставка ресурсов -> парсинг -> JavaScript
     -> style/layout -> paint/compositing -> память/GC -> отклик на ввод
```

Оптимизация — это удаление или сокращение работы на этом конвейере.

## 2. Первая оптимизация — не делать лишнего

Дешевле всего не выполнить работу вовсе:

- не передавать данные, которые клиент не использует;
- не грузить ресурсы раньше, чем они нужны;
- не создавать DOM, который пользователь не видит;
- не вычислять результат, который никому не нужен;
- не повторять уже выполненное вычисление без причины;
- не парсить и не инициализировать JS, не нужный текущему пути пользователя;
- не выделять память под короткоживущие объекты без надобности.

Это важнее микрооптимизации кода, который вообще не должен выполняться.

## 4. Critical path

К критическому пути относится HTML/CSS/JS/ресурсы, без которых пользователь не
может увидеть или использовать первое полезное состояние.

Всё остальное оценивается на предмет: загрузить позже, лениво, с меньшим
приоритетом, на сервере или не загружать вовсе.

Механизмы `defer`, `async`, `preload`, `prefetch`, `preconnect`,
`fetchpriority`, speculation rules — это **инструменты, а не умолчания**.

> Не добавляйте preload/prefetch/prerender «на всякий случай».

Агрессивная спекулятивная загрузка:

- расходует трафик пользователя;
- конкурирует с действительно критичными ресурсами;
- потребляет память (особенно `prerender`);
- греет страницы, на которые пользователь не перейдёт.

`fetchpriority` — подсказка браузеру, а не гарантия. Спекулятивная загрузка
оправдана только для достаточно вероятного следующего действия и должна
измеряться.

## 5. Сеть и данные

- Не выкачивать полный набор данных, чтобы пагинировать, фильтровать или
  сортировать в браузере.
- Не передавать поля, которые клиент не использует.
- Интерактивный серверный поиск — с debounce, иначе запрос уходит на каждый
  символ.
- **Интерактивное чтение с меняющимися параметрами обязано иметь
  latest-request-wins:** устаревший ответ никогда не перезаписывает более
  новое состояние.
- Старый запрос отменяется, когда транспорт это поддерживает.
- **Отмена не является ошибкой сети** и не показывается пользователю как
  «сервис недоступен».
- Опрос всегда ограничен бюджетом, использует backoff и может быть отменён —
  эталон `probeUntil` в `@starter/shared/data`.

Причины и реализация — [`state-and-stores.md`](state-and-stores.md).

## 6. Nuxt, SSR и рендеринг

- SSR остаётся умолчанием.
- Аутентифицированное чтение **не** переносится в SSR, пока на сервере
  действительно нет корректных учётных данных пользователя.
- Публичные и не зависящие от пользователя критичные данные имеет смысл
  грузить на сервере: страница приходит заполненной.
- «SSR быстрее» не превращается в «всё обязано быть SSR»: доставка первого
  контента и последующая интерактивность — разные вещи.

## 7. Разделение кода и ленивая загрузка

Здесь общий совет «лениво грузите всё некритичное» **проигрывает** локальному
правилу проекта, и это осознанно.

Синхронно:

- layout;
- таблицы и списки внутри быстро меняющегося UI;
- переключатели содержимого и вкладки;
- небольшие часто монтируемые и размонтируемые куски.

Лениво допустимо:

- тяжёлое содержимое модальных окон;
- редакторы;
- графики;
- кропперы;
- изолированные тяжёлые виджеты, открываемые явным действием пользователя.

Причина ограничения — не вкус: асинхронный компонент дорезолвливается после
удаления его места из DOM и роняет приложение на `insertBefore`. Разбор —
[`components-package.md`](components-package.md).

## 8. DOM и большие коллекции

- Пагинация на API — умолчание этого репозитория.
- Не рендерить большую коллекцию только потому, что данные уже получены.
- Виртуализация появляется тогда, когда UX действительно требует длинного
  непрерывного списка, а не «на будущее».
- Универсального предела количества DOM-узлов здесь нет: он устанавливается
  измерением на реальном экране, а не числом из статьи.

## 9. Main thread и JavaScript

Main thread — общий ресурс: в нём конкурируют JS, обработчики событий,
style/layout, paint и сборка мусора. Пока долгая синхронная задача удерживает
поток, интерфейс не отвечает на действия пользователя.

Порядок решений:

1. можно ли не выполнять работу вообще?
2. можно ли уменьшить объём данных или работы?
3. можно ли снизить сложность?
4. можно ли вынести на сервер или в worker?
5. можно ли разбить остаток на части с уступкой event loop?

Worker для маленькой задачи добавлять не нужно: сериализация и передача данных
тоже стоят.

Алгоритмическая сложность измеряется **на реалистичных данных**: алгоритм с
лучшей асимптотикой на маленьком входе бывает медленнее.

Микрооптимизация не превращается в общее правило. Наблюдение из одного hot path
не даёт запрета вида «никогда не использовать spread». Правильный порядок:
профиль → гипотеза → изменение → повторное измерение.

## 10. Память и GC

Сокращение аллокаций ценно, когда профиль показывает давление на GC. До
профиля это гадание, которое ухудшает читаемость кода без измеримой пользы.

Мемоизация — не автоматическое улучшение: это обмен CPU на память, и он должен
соответствовать реальному паттерну использования.

## 11. CSS и анимации

- Когда визуальный результат одинаков, предпочтительны свойства, не требующие
  пересчёта layout: `transform`, `opacity` вместо постоянного изменения `left`,
  `top`, `width`.
- Это предпочтение по стоимости рендеринга, а не синтаксический запрет.
- `will-change` **не бесплатен**: он выносит элемент в отдельный слой, а каждый
  слой стоит памяти и управления. Массово «для производительности» не ставится.
- Медленную анимацию сначала смотрят в инструментах браузера, а не лечат
  наугад.

## 12. Изображения

- Резервировать геометрию (`width`/`height` или `aspect-ratio`): иначе браузер
  перестраивает layout после загрузки и сдвигает соседний контент.
- Большие изображения отдавать через `srcset`/`sizes`/`<picture>`.
- Не отправлять desktop-размер на маленький viewport.
- Изображения ниже первого экрана — кандидаты на ленивую загрузку.
- **Вероятный LCP-ресурс лениво не грузится.**
- Современные форматы с fallback — решение конвейера ассетов.

В шаблоне почти нет изображений, и модуль обработки картинок сюда не
добавляется только ради этого раздела.

## 13. Шрифты

- Кастомный шрифт нужен под реальное дизайн-требование, а не по привычке.
- Минимизировать количество семейств и начертаний.
- WOFF2, variable fonts и subsetting — когда они реально сокращают передачу.
- Не тянуть шрифтовой файл ради одного логотипа: это задача SVG.

Демонстрационные шрифты в шаблон не добавляются.

## 14. Зависимости и рост пакетов

Для `@starter/components` и остальных пакетов workspace:

- рост пакета отражается на сборке каждого потребителя;
- внешние зависимости остаются внешними — так и задумано
  ([ADR-0006](../decisions/0006-packages-export-dist.md));
- новый публичный компонент сам по себе не является проблемой
  производительности;
- рост глобального CSS обязан быть виден в отчёте production-сборки;
- дробить entrypoints и CSS заранее, без измеренной необходимости, не нужно.

Новая тяжёлая зависимость на критичном маршруте оценивается по: начальный JS,
стоимость парсинга и инициализации, транзитивные зависимости, нужна ли она на
этом маршруте вообще.

Framework/библиотека **не заменяется по интуиции**: сначала измеряется реальное
узкое место.

## 15. Production build обязателен

Пользователь не должен получать development-сборку библиотеки или фреймворка:
dev-режим содержит проверки, диагностику и предупреждения, полезные разработчику
и бесполезные пользователю.

Отсюда практическое следствие для этого репозитория: измерения делаются на
production-сборке. `build:local` собирает пакеты **без минификации намеренно** —
он не является базой для performance-заявлений.

## 16. Доставка: минификация, сжатие, кеш

Минификация, gzip/Brotli, корректный HTTP-кеш, длинный кеш для immutable
ассетов с content hash, CDN — базовые меры.

Но в этом шаблоне они **не** имитируются: локальный Docker не изображает
production-политику кеширования. Ответственность за сжатие, кеш и CDN лежит на
production-развёртывании, и это осознанно оставленная точка расширения
([`docs/TEMPLATE.md`](../TEMPLATE.md)).

Сам по себе HTTP/2 или HTTP/3 не является гарантией быстрого сайта.

## 17. Измерение

### Lab и field — разные данные

| | Lab (Lighthouse, DevTools, WebPageTest) | Field / RUM |
|---|---|---|
| Воспроизводимость | высокая | низкая |
| Отладка | глубокая | сложная |
| Покрытие условий | выбранный сценарий | реальные устройства, сети, регионы, браузеры |

> **100 в Lighthouse не означает, что сайт быстрый у реальных пользователей.**

Одна лабораторная цифра не является определением производительности в этом
репозитории.

### Несколько измерений, а не одно

Основные Web Vitals покрывают разные аспекты:

- **LCP** — появление основного контента;
- **INP** — отклик на взаимодействие;
- **CLS** — визуальная стабильность.

Сводить производительность к одной метрике нельзя.

### Продуктовые метрики

Общие метрики не всегда описывают главный сценарий продукта: время до первого
кадра плеера, до открытия письма, до готового редактора, до пригодного к работе
canvas.

Шаблон фиксирует **необходимость** таких метрик, но не изобретает их для
несуществующих продуктов.

### Percentiles

Среднее скрывает хвост, `max` определяется одним экстремальным пользователем,
`min` описывает лучший случай, p99 часто шумный.

p75 — удобный основной ориентир для продуктовой отчётности, но смотреть нужно
распределение целиком. Улучшение, доказанное только средним значением, не
доказано.

Это подход к отчётности по умолчанию, а не универсальный статистический закон.

### Телеметрия смещена

Расширения браузера, блокировщики и защитное ПО могут одновременно замедлять
страницу и блокировать отправку телеметрии. Отсутствие плохих данных **не
является доказательством** отсутствия плохого опыта.

### Ошибки рядом с производительностью

Страница, которая быстро грузится и падает, качественной не является.
Production-мониторинг должен собирать `error`, `unhandledrejection`, CSP-отчёты,
crashes и interventions вместе с метриками скорости.

Вендор здесь намеренно не выбран.

## 18. Инвентаризация клиентских ассетов

```bash
cd frontend
pnpm perf:bundle
```

Команда собирает **production**-сборку приложения и печатает размеры
эмитированных клиентских файлов: raw, gzip и Brotli, с группировкой по типу.

Что это **не**: это не измерение Web Vitals и не оценка критического пути. Без
графа чанков и запуска в браузере скрипт не знает, что именно загружается на
первом маршруте. Это инвентарь, полезный для сравнения «до/после».

## 19. Что считается performance-sensitive изменением

Изменение является performance-sensitive, если содержит хотя бы одно:

- новая runtime-зависимость;
- крупная библиотека на критичном маршруте;
- новый глобальный CSS;
- кастомный шрифт;
- существенный по размеру ассет;
- preload/prefetch/prerender;
- изменение границ разделения кода;
- изменение рендеринга большого списка;
- тяжёлое синхронное вычисление;
- изменение поведения запросов или опроса;
- перенос загрузки между SSR и клиентом;
- изменение экспортов или сборки пакета.

Для таких изменений в описание задачи попадает измерение до и после,
соответствующее характеру изменения. Для изменения размера бандла это
`pnpm perf:bundle` — см. [`../conventions/checks.md`](../conventions/checks.md).

## 20. Чего в шаблоне намеренно НЕТ

Шаблон **не определяет**:

- пороговые значения Web Vitals;
- лимиты размера бандла в байтах;
- предельное число DOM-узлов;
- проходной балл Lighthouse;
- RUM-провайдера;
- продуктовую метрику.

Причина одна: осмысленные значения выводятся из критических маршрутов, целевых
устройств, условий сети и продуктовых требований. Ни одного из этих входных
данных у шаблона нет, а выдуманное число хуже отсутствующего — его начинают
защищать.

## 21. Чек-лист включения production-наблюдаемости

Для реального проекта после развёртывания:

- [ ] определить критические маршруты и сценарии;
- [ ] определить целевые устройства и сегменты сети;
- [ ] снять baseline production-бандла;
- [ ] выбрать лабораторные сценарии;
- [ ] инструментировать LCP/INP/CLS;
- [ ] определить продуктовые метрики;
- [ ] отчитываться по распределению, а не по среднему;
- [ ] собирать клиентские ошибки;
- [ ] установить бюджеты **после** baseline;
- [ ] завести проверки в выбранном CI-провайдере.

В шаблоне это остаётся документацией.

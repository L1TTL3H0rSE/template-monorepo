# Согласованность в конце: запись и её появление в выдаче

## Что происходит

Между записью и её появлением в выдаче стоит асинхронный конвейер:

```text
POST /characters
  -> сервис пишет в PostgreSQL
  -> 200 OK клиенту                    <- здесь запись УЖЕ есть в БД
  -> событие в шину
  -> индексатор читает событие
  -> запись появляется в поисковом индексе   <- здесь она появляется в ВЫДАЧЕ
```

`200 OK` означает «записано», а не «видно в списке». Между этими моментами —
от десятков миллисекунд до секунд, а при отставании индексатора — больше.

## Антипаттерн

```ts
async function create(draft) {
  await api.characters.create(draft);
  await load();            // <- почти всегда возвращает список БЕЗ записи
}
```

`load()` успевает раньше конвейера. Пользователь видит, что действие «не
сработало», нажимает ещё раз — и создаёт дубликат. Дубликат при этом создаётся
по-настоящему, потому что запись прошла оба раза.

Хуже всего, что локально это не воспроизводится: на пустой БД и локальном
индексаторе задержка близка к нулю. Ошибка появляется только на стенде с
данными.

## Паттерн: оптимистичный оверлей + ограниченный опрос

```ts
async function create(draft: CharacterDraft): Promise<Character> {
  const created = await api.characters.create(draft);

  // 1. Показать немедленно — до появления в выдаче.
  optimistic.trackAdd(created);
  pagination.setTotal(pagination.total.value + 1);

  // 2. Подтвердить фоном, не блокируя интерфейс.
  void reconcile(created.id, async () => {
    const page = await api.characters.search({ query: created.name, limit: 20, offset: 0 });
    return page.items.some((item) => item.id === created.id);
  });

  return created;
}
```

Три части, каждая обязательна:

### 1. Оверлей поверх серверного списка

`useOptimisticList` накладывает локальные правки на серверную выдачу:

```ts
const items = computed(() => optimistic.merge(serverItems.value));
```

Созданная запись видна сразу и стоит первой — а не на третьей странице, куда её
поставит серверная сортировка. Дубликата не возникает: запись, уже пришедшая с
сервера, вытесняет свой оверлей по ключу.

### 2. Ограниченный опрос с задержкой

`probeUntil` вызывает проверку с экспоненциальной задержкой, пока она не
подтвердит согласованность либо пока не кончится бюджет попыток.

Бюджет обязателен: бесконечный retry превращает временную деградацию конвейера
в шторм запросов от каждой открытой вкладки.

### 3. Снятие оверлея в любом исходе

```ts
const consistent = await probeUntil(check, options);
settle(key);      // <- и при успехе, и при исчерпании бюджета
return consistent;
```

Оверлей, оставленный навсегда, показывает запись, которой на сервере может уже
не быть, и расходится с реальностью тем сильнее, чем дольше открыта вкладка.

Если бюджет исчерпан, честный ответ пользователю — «изменения появятся через
несколько секунд», а не тишина и не ложное «готово».

## Удаление устроено симметрично

```ts
optimistic.trackRemove(id);
void reconcile(id, async () => {
  const page = await api.characters.search({ limit, offset });
  return !page.items.some((item) => item.id === id);
});
```

Удалённая запись скрывается немедленно; опрос ждёт, пока она исчезнет из
выдачи.

## Что показывать пользователю

```ts
const syncing = ref(false);   // есть неподтверждённые правки
```

Не «загрузка» — данные уже показаны. Уместен ненавязчивый индикатор
«синхронизируется» рядом со списком, а не блокирующий спиннер поверх экрана.

## Когда паттерн не нужен

Если чтение идёт из того же хранилища, что и запись (без индекса и без шины),
конвейера нет — и оверлей только усложняет код. Признак: адаптер читает и
пишет один и тот же ресурс, а бэкенд не публикует события.

В шаблоне `mock`-провайдер именно такой: запись видна мгновенно. Именно поэтому
паттерн нужно проверять против реального бэкенда — на фикстурах его отсутствие
незаметно.

## Чек-лист мутации в сторе

- [ ] Нет `await load()` сразу после мутации.
- [ ] Результат показан локально до подтверждения.
- [ ] Счётчик `total` скорректирован локально.
- [ ] Опрос ограничен по числу попыток.
- [ ] Оверлей снимается в обоих исходах.
- [ ] Исчерпание бюджета отражено в интерфейсе, а не проглочено.

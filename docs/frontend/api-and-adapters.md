# Контракты, адаптеры и провайдеры

Самый важный паттерн фронтенда: приложение зависит от **своего** интерфейса, а
не от формы, в которой данные приходят по сети.

## Схема

```text
app/contracts/       ПОРТ: доменные типы + интерфейс. Ни от чего не зависит.
       ↑                    ↑
app/pages            app/adapters/http/    реальный бэкенд
app/stores           app/adapters/mock/    фикстуры
       ↑                    ↑
app/api/api.ts       выбор реализации — ровно одно место
```

Направление стрелок принципиально: **и потребитель, и реализация зависят от
контракта**, а не друг от друга.

## Контракт

```ts
// app/contracts/character.ts

export type Character = {
  id: string;
  name: string;
  status: CharacterStatus;
  createdAt: Date;          // Date, а не строка
};

export type RequestContext = {
  signal?: AbortSignal;
};

export interface CharacterApi {
  search(
    params: CharacterSearch,
    context?: RequestContext,
  ): Promise<CharacterPage>;
  getById(id: string): Promise<Character>;
  create(draft: CharacterDraft): Promise<Character>;
  rename(id: string, name: string): Promise<Character>;
  remove(id: string): Promise<void>;
}
```

`AbortSignal` — веб-стандарт, а не деталь HTTP, поэтому он может стоять в
контракте домена. Ничего специфичного для транспорта (заголовки, коды, URL)
сюда не попадает: это сломало бы границу порта.

Контекст принимает **только `search`** — у него есть доказанный потребитель:
интерактивный поиск, где параметры меняются быстрее, чем приходит ответ.
Остальные методы получат его тогда, когда появится потребитель, а не ради
симметрии.

Доменная модель — `camelCase`, готовые типы, минимум `| null`. Она описывает,
что нужно **приложению**, а не что отдаёт бэкенд.

Интерфейс объявлен рядом с потребителем — тот же принцип, что и в Go-сервисах
(см. [`backend/layers.md`](../backend/layers.md)).

## Адаптер

Единственное место перевода транспортной формы в доменную:

```ts
function toCharacter(dto: ExampleViewDto): Character {
  return {
    id: dto.id,
    name: dto.name,
    // Бэкенд ещё не отдаёт статус: значение по умолчанию задаётся ЗДЕСЬ,
    // а не в шаблоне. Когда поле появится, правка будет ровно одна.
    status: "published",
    createdAt: new Date(dto.created_at),   // строка -> Date
  };
}
```

Что делает адаптер: `snake_case → camelCase`, строка → `Date`, отсутствующее
поле → значение по умолчанию, склейка нескольких запросов в одну модель.

Если этот перевод растекается по компонентам, каждый из них начинает знать
формат бэкенда — и переименование поля в API превращается в правку тридцати
файлов.

## Транспорт

`@roleplay/api/core` — `ApiClient`. Он владеет тем, что иначе дублируется:

- базовый URL;
- подстановка токена;
- разбор конверта `{error, data}`;
- превращение ответа с ошибкой в типизированный `ApiError`.

```ts
// Разворачивание конверта — здесь и только здесь.
return (payload as SuccessEnvelope<T>).data;
```

Иначе каждый вызывающий пишет `.data.data` и однажды ошибается.

`ApiClient` **не знает доменных типов**. Адаптер **не знает про `fetch`**.
Из-за этого смена бэкенда затрагивает адаптеры, а смена транспорта — только
клиент.

### Пустые query-параметры не отправляются

```ts
if (value === undefined || value === null || value === "") continue;
```

`?q=&page=` заставляет бэкенд отличать «не передано» от «передано пустым» без
всякой причины.

### Три типа ошибок, а не один

Интерфейсу нужно различать 404 («не найдено»), 401 («войдите») и 500
(«попробуйте позже»). Со строкой в `message` это делается сравнением текста,
который меняется при первой правке формулировки.

| Тип | Что произошло | Что показать |
|---|---|---|
| `ApiError` | Сервер ответил ошибкой | Сообщение по коду: не найдено, нет прав, попробуйте позже |
| `NetworkError` | До сервера не дошли | «Сервис недоступен» |
| `RequestCancelledError` | Запрос отменён вызывающим | **Ничего** |

Третий тип — не педантизм. Отмена является **нормальным** исходом
интерактивного чтения: каждый новый применённый поисковый запрос отменяет
предыдущий. Если отмена приходит как `NetworkError`, пользователь видит «Сервис
недоступен» при обычной работе с поиском.

Различить их по тексту сообщения нельзя, поэтому тип отдельный, а рядом есть
предикат:

```ts
import { isCancelled } from "@roleplay/api/core";

catch (caught) {
  if (isCancelled(caught)) return;   // молча
  // настоящая ошибка
}
```

### Отмена распознаётся по двум признакам

`ApiClient` проверяет и имя ошибки (`AbortError` от `fetch`), и состояние
сигнала — до запроса, после `fetch` и при чтении тела. В гонке между отменой и
сетевым сбоем сработать может любой признак, и одной проверки недостаточно.

Отдельно перехватывается разбор тела: голый `.catch(() => null)` вокруг
`response.json()` превратил бы отмену в пустой payload, и на статусе 200 код
дошёл бы до `payload.data` с `TypeError` вместо внятной отмены.

### Mock-адаптер тоже обязан отменяться

Фикстура имитирует задержку, и эта задержка должна быть **отменяемой**. Иначе
mock-провайдер прячет гонки, существующие с реальным HTTP: устаревший запрос
всегда доходит до конца, и latest-request-wins выглядит работающим ровно до
переключения на настоящий бэкенд.

Ошибка фикстуры носит имя `AbortError` — то же, что отдаёт `fetch`, — поэтому
вызывающий обрабатывает отмену одинаково для обоих провайдеров.

## Схемы ответов

```ts
export const exampleViewSchema = z.object({
  id: z.string().uuid(),
  name: z.string(),
  created_at: z.string(),
});
```

TypeScript проверяет форму **на сборке**, данные приходят **в рантайме**. Ответ,
разошедшийся с контрактом, без схемы падает где-то глубоко в компоненте и
выглядит как баг фронтенда. Со схемой он падает на границе и называет эндпоинт:

```ts
parseResponse(exampleViewSchema, payload, `GET /example/${id}`);
```

Схема описывает форму **транспорта** (`snake_case`, как в JSON), а не доменную
модель.

## Выбор реализации

```ts
function createApi(): WebApi {
  const config = useRuntimeConfig();

  if (config.public.apiProvider === "mock") {
    return { characters: new MockCharacterAdapter() };
  }

  const client = new ApiClient(config.public.apiBaseUrl as string, getToken);

  return { characters: new HttpCharacterAdapter(client) };
}
```

```bash
NUXT_PUBLIC_API_PROVIDER=mock   # фикстуры, бэкенд не нужен
NUXT_PUBLIC_API_PROVIDER=http   # реальный бэкенд
```

**Выше `app/api/api.ts` слово «mock» не встречается.** Страница и стор знают
только тип порта. Именно поэтому переключение — переменная окружения, а не
ветвление в компонентах.

Что это даёт:

- фронтенд разрабатывается до готовности бэкенда;
- e2e-сценарии интерфейса гоняются без стенда;
- дизайнерская проверка не требует поднятого окружения.

Цена: два адаптера обязаны вести себя одинаково. Расхождение — самая дорогая
ошибка этой схемы, потому что проявляется только в проде.

## Тест на порт

Поэтому тест пишется **на интерфейс**, а не на реализацию:

```ts
describe("CharacterApi (mock)", () => {
  it("возвращает страницу и общее количество", async () => {
    const page = await api.search({ limit: 2, offset: 0 });

    expect(page.items).toHaveLength(2);
    expect(page.total).toBe(3);   // total — всего подходящих, а не длина страницы
  });
});
```

Тот же набор проверок имеет смысл прогонять против HTTP-адаптера, когда
появится тестовый стенд.

## Пагинация и фильтрация

В HTTP-адаптере остаются на сервере. Загрузить весь набор и резать в браузере —
решение, которое работает на трёх фикстурах и ложится на трёх тысячах записей.

Mock-адаптер режет массив в памяти — потому что он и есть фикстура. Это
единственное допустимое расхождение между адаптерами, и оно не влияет на
контракт.

## Добавление домена

1. Тип и интерфейс в `app/contracts/<домен>.ts`, поле в `WebApi`.
2. Схемы транспортных DTO в `@roleplay/api/gateway`.
3. `app/adapters/http/<домен>-adapter.ts`.
4. `app/adapters/mock/<домен>-adapter.ts`.
5. Оба в `app/api/api.ts`.
6. Тест на порт.

Шаг 4 не пропускается: без mock-реализации переключатель провайдера ломается для
всего приложения, а не только для нового домена.

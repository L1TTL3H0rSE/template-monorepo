# Решения (ADR)

Architecture Decision Record — запись о принятом сквозном решении: что решили,
почему, что рассмотрели и от чего отказались.

## Зачем

Через полгода никто не помнит, почему в шаблоне нет слоя репозиториев. Без
записи возможны два одинаково плохих исхода: слой добавят «потому что так
принято», либо не добавят там, где он действительно нужен, — тоже «потому что
так принято».

ADR фиксирует **границы** решения и его цену, чтобы обе ошибки были видны.

## Когда заводить

- Решение касается нескольких компонентов.
- Есть отвергнутые альтернативы, о которых будут спрашивать.
- Отменить решение дорого.

Решение внутри одного файла ADR не требует — там достаточно комментария.

## Правила

1. Номер не переиспользуется.
2. Принятый ADR **не переписывается**. Изменение решения — новый ADR со статусом
   `supersedes NNNN`; старый получает `superseded by NNNN`.
3. Статусы: `proposed` → `accepted` → `superseded` / `deprecated`.
4. «Рассмотренные варианты» — обязательный раздел. ADR без альтернатив не
   объясняет выбор, а просто утверждает его.
5. `accepted` обязан нести поле **«Пересмотр в потомке»** — событие, при
   наступлении которого проект, инициализированный из этого репозитория,
   пересматривает решение. Именно событие («появился второй сервис»), а не
   состояние («когда понадобится»): второе неотличимо от «забыли». Поле
   переносится в `ADOPTION.md` при инициализации, и его отсутствие валит
   `scripts/init-project.mjs`.

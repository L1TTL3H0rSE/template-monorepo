# ADR-0008: Обязательные и опциональные проверки качества

- **Статус:** accepted
- **Дата:** 2026-09-26
- **Область:** проверки кода, сборки и инициализации
- **Пересмотр в потомке:** первый собственный пакет, сервис или изменение состава обязательных анализаторов

## Контекст

Правила должны исполняться штатной командой и обнаруживать представительное
нарушение. Наличие конфигурации или зелёный прогон по пустому входу этого не
доказывает. Внешние сервисы и условия конкретного CI не принадлежат шаблону.

## Решение

- Сохраняем строгие существующие TypeScript/Vue-пресеты. Добавляем проверки
  необработанных промисов, импортов, границ workspace и доступности.
- Typed lint использует явный `tsconfig.lint.json`, общий с дополнительным
  typecheck: в него входят исходники, тесты и конфигурация. Подготовка Nuxt
  выполняется перед проверкой приложения. ESLint content cache не используется:
  изменение импортируемого типа должно перепроверять потребителя.
- Сборка библиотек проверяет относительные импорты JS/деклараций, конкретные
  публичные экспорты и актуальность dist. Wildcard exports должны находить
  файлы; SCSS API дополнительно проверяется сборкой приложения-потребителя.
  Bare-зависимости остаются внешними.
- Go проверяется отдельно в каждом модуле: build, vet, test и явный список
  golangci-lint. Версия 2.12.2 совместима с объявленным Go 1.25; более новая
  версия из исходного проекта требует Go 1.26 и сюда не переносится.
- Исключение узкое, называет анализатор и объясняет причину. Долг исходного
  проекта и его исключения не наследуются. Ослабление обязательного правила
  оформляется отдельным изменением политики.
- У проверок есть положительные и отрицательные примеры. Новые конфиги
  проходят инициализацию и проверяются с новой идентичностью.
- Дополнительные браузерные, security, контрактные и исследовательские проверки
  описаны в `docs/conventions/optional-quality.md`. Документ сохраняется после
  инициализации. Включение фиксируется ADR проекта и добавлением команды к его
  обязательному набору; флаги генератора проекта для этого не нужны.

## Рассмотренные варианты

1. Копировать весь набор из большого продукта: приносит чужие зависимости,
   исключения, границы сервисов и требования к Go. Отвергнуто.
2. Только перечислить рекомендации: не защищает исходный шаблон. Отвергнуто
   для проверок с ясным инвариантом и локальным положительным/отрицательным случаем.
3. Небольшая исполняемая база и готовые рецепты расширения: выбранный вариант.
   Границы прямых импортов живут в ESLint; анализ полного графа и циклов подключается
   отдельно при росте приложения и заменяет дублирующие ограничения.

## Последствия

Typed lint и анализ Go увеличивают время проверки. Первый запуск Go-анализатора
загружает закреплённый инструмент; после подготовки кеша проверки работают без
сервиса качества. Toolchain проекта не обновляется автоматически.

Проверка прямых импортов не доказывает отсутствие обхода через цепочку фасадов
или Nuxt auto-imports. Это явная граница базового архитектурного правила,
а не обещание полного графового анализа.

## Когда решение перестаёт действовать

Изменились границы пакетов, способ публикации библиотек или минимальная версия
toolchain; обязательный анализатор перестал обнаруживать заявленный дефект.

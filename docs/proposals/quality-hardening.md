# Предложение: машинно-проверяемые гарантии качества

- **Статус:** proposed
- **Дата:** 2026-08-18
- **Область:** весь репозиторий (конфигурация анализаторов, документы, init)

Это **предложение**, а не принятое решение. Ничего из перечисленного здесь пока
не реализовано и не действует. Документ существует, чтобы идеи были
зафиксированы на уровне репозитория и их можно было брать по одной, а не
пересобирать заново из чужой переписки.

Взятый пункт оформляется обычным порядком: ADR в
[`../decisions/`](../decisions/), затем код и конфигурация, затем строка отсюда
удаляется. Предложение не является источником истины: как только пункт
реализован, истина — конфигурация анализатора.

**При инициализации проекта каталог `docs/proposals/` удаляется целиком.** Это
план развития самого шаблона, а не унаследованное решение: потомку он достаётся
как чужой список задач, который никто не будет разбирать. Механика описана в
[`../TEMPLATE.md`](../TEMPLATE.md).

## Принцип

> Если архитектурный или качественный инвариант проверяется детерминированно и
> с низкой долей ложных срабатываний — предпочесть исполняемую проверку, а не
> инструкцию в прозе.

Обратное тоже обязательно: правило, требующее инженерного суждения, остаётся в
документах и ADR и **не** превращается в эвристический линт. Метрика без
решения, которое она меняет, — не гарантия, а приглашение её обходить.

## Разделение ответственности

```text
Компилятор / typechecker   -> корректность на уровне языка
Статические анализаторы    -> известные запрещённые состояния
Архитектурный линт         -> направление зависимостей и границы модулей
Тесты                      -> требуемое поведение
Мутационные тесты          -> что тесты действительно защищают поведение
AGENTS / docs              -> инженерное суждение в неоднозначных случаях
ADR                        -> почему инвариант существует
Внешний оркестратор / CI   -> когда обязательные проверки запускаются
Защита веток в SCM         -> может ли непроверенный код попасть в основную ветку
SonarQube                  -> агрегация, тренды, удалённый quality gate
```

Ключевая граница: шаблон владеет **инвариантами и листовыми командами**. Когда и
где они запускаются — забота внешнего оркестратора или CI. Поэтому в шаблоне не
появляются ни манифесты оркестратора, ни workflow конкретного CI, ни адрес и
токен Sonar.

## Что изменил первый потомок

Шаблон впервые прожил в настоящем продукте. Часть плана это подтвердило, часть —
удешевило.

**Общее правило негативного доказательства взято и лежит вне этого документа.**
«Проверка обязана уметь падать» теперь в
[`../conventions/checks.md`](../conventions/checks.md): у осмысленного гейта
должно быть исполняемое доказательство, что представительное нарушение делает
его красным. Повод — дефект, который план не предвидел: обязательная проверка
запускалась, давала правдоподобный вывод и не доходила до проверяемого места.
Зелёный результат в таком случае неотличим от работающего инварианта.

Следствия для плана:

- QH-05 и QH-11 (фикстуры для checker'а и для архитектурных правил) перестают
  быть самостоятельными пунктами обоснования: это частные случаи общего
  правила. Реализовать их всё равно нужно — но как обычную часть QH-04 и QH-09,
  а не как отдельное решение;
- QH-35 — QH-37 (мутационное тестирование) слабеют дальше. Вопрос «защищают ли
  тесты поведение» для **проверок** закрыт правилом выше без единого
  инструмента и без числа, по которому никто не принимает решения. Остаётся
  разовое расследование конкретного модуля — не регулярный гейт.

**Отсутствие CI-конвейера в шаблоне подтвердилось.** Потомок завёл GitHub
Actions под свою площадку, и переносимым оказалось не описание заданий, а
листовые команды `checks.md`: конвейер выполняет их и ничего сверх. Из его опыта
в шаблон вернулись два инварианта, которыми владеет шаблон, а не оркестратор:
модули проверяются по отдельности и сборка идёт на объявленном поле версии Go
(`GOTOOLCHAIN=local`). Оба уже в `checks.md`.

**QH-40 записан, но не взят.** Потомок разделил фронтенд-проверки на
happy-dom и настоящий Chromium и на этом поймал класс дефектов, невидимый
модульным тестам: история существует, а рендерится с ошибкой. Урок общий, но
цена для шаблона — браузерный бинарь в baseline ради шести демонстрационных
компонентов. Триггер записан в таблице; регрессия снимков сюда не относится и
остаётся продуктовым делом потомка. Если браузерные проекты появятся, вместе с
ними переносится и правило портов: умолчания Vitest берут порты из динамического
диапазона Windows, часть которого резервируют Hyper-V, WSL и Docker, и занятый
порт виден как `EACCES`, а не `EADDRINUSE`. Лечится явным низким портом при
выключенном `strictPort`.

**QH-39 (дымовой прогон инициализированной копии) подорожал в цене ошибки.**
Потомок нашёл в унаследованной механике три дефекта, каждый из которых виден
только на инициализированной копии или в контейнере, но не на самом шаблоне:
`.dockerignore`, привязанный к корню контекста; CLI миграций без build-тега;
`DB_NAME` с умолчанием на служебную базу.

Состояние доказательств по каждому — состояния не взаимозаменяемы:

| Дефект | Исправлен | Проверка с красным состоянием | Прогнан на инициализированной копии |
|---|---|---|---|
| `.dockerignore` от корня контекста | да | `scripts/dockerignore.test.mjs` | да |
| Схема адреса миграций | да | `postgres_test.go: TestMigrationDSNUsesPGX5` | да |
| Установка CLI без `-tags pgx5` | да | нет: проверять нечего без `go install` в сеть | нет |
| `DB_NAME` пуст или из пробелов | да | `postgres_test.go`: `TestNameMustBeMeaningful` (загрузка), `TestPublicOperationsRejectEmptyName` (обе публичные операции адаптера) | да |
| Действующий ADR без условия пересмотра | да | `scripts/adoption.test.mjs` (инвариант), `scripts/init-project.test.mjs` (отказ до первой мутации и в `--dry-run`) | да |

Одно проверено дальше тестов: `mage database:up` доходил до живого PostgreSQL —
значит, CLI собран с нужным драйвером и схема `pgx5://` им принимается. А вот
`.dockerignore` на настоящей сборке образа не проверялся: его инвариант держится
на тесте и на разборе семантики контекста, не на прогоне docker. Пункт остаётся
предложением, но его триггер наступил.

## Замечания к исходному плану

Эти пункты записаны отдельно, потому что брать их «как есть» нельзя.

**QH-09 против отдельных правил ESLint.** Исходный план предлагал одновременно
`no-restricted-imports` в ESLint **и** `dependency-cruiser` с теми же правилами.
Это два источника истины для одного инварианта, чего сам же план запрещает.
`dependency-cruiser` покрывает всё, что делают ограничения импортов, и вдобавок
циклы и глубокие импорты. Правила границ живут в одном месте — в его конфигурации.

**QH-12 — это изменение архитектуры, а не настройка линтера.** Отвязка стора от
`@starter/api/core` трогает ADR-0005 (порты и адаптеры) и ADR-0007
(оптимистичный оверлей). Такое оформляется своим ADR с рассмотренными
вариантами, а не как побочный эффект включения архитектурной проверки. Пока ADR
нет, правило не делается жёстким.

**QH-26, QH-28, QH-33 — инфраструктура под несуществующего потребителя.**
Машинночитаемые отчёты и конфигурация Sonar осмысленны, когда есть тот, кто их
читает. Пока агрегатора нет, это файлы, которые устаревают быстрее, чем
понадобятся. Человекочитаемый вывод анализаторов при этом остаётся полезным сам
по себе.

**QH-34 — по собственному критерию плана брать нечего.** Правило Semgrep
добавляется, когда наблюдался конкретный дефект, которого не ловят компилятор,
ESLint, golangci-lint и тесты. Ни одного такого дефекта пока не зафиксировано,
поэтому создавать каталог с фикстурами заранее не за чем. Первый повторяющийся
промах агента — и место заводится вместе с правилом.

**QH-35 без порога.** План явно запрещает универсальный mutation score и это
верно. Но тогда мутационное тестирование даёт число, по которому никто не
принимает решения. Оно осмысленно как разовое расследование конкретного модуля,
а не как регулярная проверка.

## Уровни проверок

Уровни описываются как понятие, без привязки к конкретному оркестратору.

**Быстрый локальный:** type-aware ESLint, typecheck, архитектурный линт, тесты,
проверка политики качества; на бэкенде — `go vet`, `golangci-lint`, тесты; на
контрактах — `sqlc vet`, `buf lint`.

**Полный локальный:** сборка фронтенда, Knip, publint, сборка Storybook, все
тесты, отчёты покрытия, сборка Go, `go test -race`, валидация SQL против базы,
дымовой тест инициализированной копии, NilAway если стабилен, выборочные
мутационные прогоны.

**Внешний:** SonarQube, CodeQL, Trivy, `govulncheck` со свежей базой, сканирование
истории на секреты, полная мутационная кампания, `buf breaking` против baseline.

Правило, которое держит всю схему:

> Базовая локальная корректность обязана оставаться полезной без сети. Внешние
> сервисы усиливают систему, но не определяют базовую корректность.

## Чего в шаблоне не появляется

Ни один пункт выше не является поводом добавить в шаблон:

- манифесты оркестратора любого вида;
- workflow GitHub Actions, GitLab CI, Jenkins ради подключения проверок;
- адрес сервера, токен или ключ проекта SonarQube;
- CodeQL как обязательную привязку к одной хостинг-платформе;
- конфигурацию защиты веток;
- произвольные пороги покрытия, mutation score, размера бандла, Lighthouse;
- правила FSD, пока репозиторий явно не принял FSD;
- `golangci-lint` с `enable-all`;
- большие генерические наборы правил Semgrep ради количества анализаторов.

Отдельно: [`../frontend/performance.md`](../frontend/performance.md) остаётся
измерительным. Порядок «сценарий → базовая линия на production-сборке → узкое
место → гипотеза → минимальное изменение → повторное измерение» не заменяется
числовыми бюджетами. Если потомок примет бюджет, это его отдельное явное
решение, а не скрытое умолчание шаблона.

## Состояние инструментов

Из требуемого локально установлен только `sqlc`. Для остального нужны бинари,
которых в системе нет: `golangci-lint`, `buf`, `hadolint`, `govulncheck`. Пока
их нет, соответствующие конфигурации непроверяемы — а гейт, который никто не
запускал, гейтом не является.

Шаблон может документировать требуемые версии, но не привязывается к одному
способу их распространения: dev-контейнер, образ CI, Nix, mise — выбор проекта.

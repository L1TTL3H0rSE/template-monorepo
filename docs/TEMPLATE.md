# Репозиторий как шаблон проекта

## Что это

Мнящий себя правым шаблон под конкретный стек: **Go + PostgreSQL + sqlc/pgx на
бэкенде, pnpm-workspace + Nuxt/Vue/Pinia на фронтенде, Docker для локального
рантайма.**

Он **не** пытается поддерживать React и Vue, REST и GraphQL, npm и pnpm,
PostgreSQL и MongoDB одновременно. Матрица вариантов вместо решения — это не
шаблон, а генератор, который не отвечает ни на один вопрос.

Цель формулируется так:

> сильный набор умолчаний для известного стека с явными условиями отказа,

а не:

> фреймворк, порождающий любую архитектуру.

Рабочий демонстрационный код здесь намеренный: паттерн, который нельзя
запустить, перестаёт быть правдой в первый же месяц.

## Три вида содержимого

Их нельзя путать: у них разная судьба в новом проекте.

### 1. Механика шаблона

Переживает почти любой проект:

- структура репозитория и документации;
- правила источников истины для агентов;
- требования детерминизма генераторов;
- соглашения workspace;
- обязательные проверки;
- сам процесс инициализации.

### 2. Умолчания архитектуры

Рекомендованы, но имеют условия применимости — каждое зафиксировано ADR:

| ADR | Решение |
|---|---|
| [0001](decisions/0001-thin-service-layer.md) | Тонкий слой сервиса без моделей и репозиториев |
| [0002](decisions/0002-proto-first-contracts.md) | Контракт объявляет владелец данных |
| [0003](decisions/0003-gateway-trusted-context.md) | Сервис доверяет контексту гейтвея |
| [0004](decisions/0004-bem-attribute-modifiers.md) | Модификаторы BEM — HTML-атрибуты |
| [0005](decisions/0005-frontend-ports-and-adapters.md) | Фронтенд зависит от порта, а не от транспорта |
| [0006](decisions/0006-packages-export-dist.md) | Пакеты workspace экспортируют `dist` |
| [0007](decisions/0007-optimistic-ui-bounded-probe.md) | Оптимистичный оверлей вместо перезагрузки |

Это **базовые решения, а не вечные законы.** У каждого есть раздел «когда
решение перестаёт действовать».

### 3. Демонстрационное приложение

- бэкенд-сервис `gotemplate` и его домен `example`;
- фронтенд-домен `character`;
- брендинг и тексты Starter.

Демо существует, чтобы паттерны оставались исполняемыми. **Не удаляйте его до
появления замены** — иначе шаблон превращается в набор README, в котором ничего
не проверяется.

## Старт проекта

```bash
node scripts/init-project.mjs \
  --display-name "Acme" \
  --slug acme \
  --repository-name acme-platform \
  --npm-scope @acme \
  --go-module-prefix github.com/acme/acme-platform
```

Сначала посмотрите, что будет затронуто:

```bash
node scripts/init-project.mjs ... --dry-run
```

Скрипт:

- заменяет npm-скоуп, префикс Go-модулей, брендинг и имя репозитория;
- **не трогает** `gotemplate`, `example`, `character`;
- разделяет память шаблона и память проекта;
- генерирует `docs/decisions/ADOPTION.md`;
- запускает проверку остатков.

Идентичность берётся из `.template.json`, а не из констант внутри скрипта: у
проверки остатков и у замены обязан быть один эталон.

### Что означает `--force`

Только одно: **разрешить грязное рабочее дерево**. По умолчанию скрипт
отказывается работать на дереве с незакоммиченными правками — инициализация
меняет сотни файлов, и отделить их от ваших правок потом невозможно.

**Повторная инициализация запрещена всегда и `--force` её не снимает.** Она не
может сработать правильно по построению: замены строятся из идентичности
ШАБЛОНА, которой после первого запуска в дереве уже нет. Второй запуск ничего не
переименовал бы, но записал бы новую идентичность в метаданные — файлы говорили
бы «Acme», метаданные «Beta», а проверка остатков этого не заметила бы, потому
что ищет только исходные токены. Вдобавок разделение памяти выполнилось бы
повторно и затёрло унаследованную память уже накопленной проектной.

Переименование существующего проекта — отдельная задача с другой семантикой.
Делать её наполовину хуже, чем не делать вовсе.

### Как разрешаются пересечения замен

Правила сортируются **от самого длинного шаблона к самому короткому** и
применяются за **один проход** по исходному тексту.

Длина решает пересечения: `@starter/` побеждает `starter/`, иначе npm-скоуп
превратился бы в `@github.com/acme/...`. Явный порядок в массиве для этого
ненадёжен — он ломается при первом добавлении поля в идентичность.

Один проход нужен, чтобы уже вставленный результат не попадал под следующее
правило. Цель `@my-starter` при исходном `@starter` иначе превратилась бы в
`@my-acme` правилом `starter -> acme`, и `.template.json` расходился бы с
деревом при зелёной проверке остатков.

Голый slug заменяется **только по границам слова**: без этого он вырезает
подстроку из чужих слов (`restarter`).

Поведение зафиксировано тестами:

```bash
node --test scripts/template-identity.test.mjs
```

## Пересмотр архитектуры

После инициализации появляется `docs/decisions/ADOPTION.md` с действующими
(`accepted`) ADR шаблона в состоянии `pending`.

Отменённые и замещённые решения попадают в отдельный справочный раздел и
пересмотра не требуют: принимать в них нечего, а объясняют они, почему
действующие решения выглядят именно так.

**База архитектуры проекта не считается завершённой, пока остаются строки
`pending`.** Это не формальность: принятое решение шаблона — компромисс,
сделанный в другом контексте, и наследовать его молча означает платить цену, о
которой никто в проекте не знает.

Допустимые состояния:

- `adopted` — проверено в контексте проекта и принято;
- `superseded by ADR-NNNN` — проект принял другое решение и оформил его своим
  ADR;
- `pending` — не рассмотрено.

Состояния `rejected` нет намеренно: унаследованный файл продолжает утверждать
`accepted` и остаётся в дереве источников истины. Отказ оформляется **новым
ADR**, который замещает старый, — по обычным правилам
[`decisions/README.md`](decisions/README.md).

ADR сейчас немного, поэтому явный первичный пересмотр — посильная работа.

## Пересмотр памяти

При инициализации:

```text
docs/PROJECT_MEMORY.md  ->  docs/TEMPLATE_MEMORY.md   (унаследованное)
docs/PROJECT_MEMORY.md                                 (новое, пустое)
```

Почему разделение обязательно: записи вида «покрытие v8 врёт для `.vue`» или
«pnpm не поднимает транзитивные пакеты» проверены **на шаблоне**, с его версиями
инструментов. В новом проекте набор зависимостей другой, и часть фактов может
устареть — но они продолжат выглядеть как «проверенный факт проекта».

Унаследованная память **не удаляется**: большинство ловушек тулчейна остаются
полезными. Запись переносится в память проекта только после повторной проверки
по текущему коду.

Корневой `AGENTS.md` продолжает требовать чтения `PROJECT_MEMORY.md` и **не**
требует читать всю унаследованную память на каждой задаче.

## Замена демо

Демо удаляется **одним связным изменением**, когда появился настоящий
вертикальный срез:

1. новый Go-сервис вместо `gotemplate` (или переименование его копии);
2. новый домен вместо `example`;
3. новый фронтенд-домен вместо `character`;
4. обновление ссылок на эталоны в `AGENTS.md`, `backend/AGENTS.md`,
   `frontend/AGENTS.md`;
5. обновление документов, ссылающихся на демо;
6. обновление `.template.json` → `demo`.

Частичное удаление хуже полного: документация начинает ссылаться на
несуществующий эталон, и следующий разработчик копирует то, чего нет.

## Что намеренно отсутствует

Эти точки расширения оставлены пустыми, потому что зависят от проекта, а
подделка «универсального» решения дороже отсутствия:

| Отсутствует | Где точка подключения |
|---|---|
| CI-провайдер | [`conventions/checks.md`](conventions/checks.md) — команды готовы |
| Провайдер аутентификации | `backend/kit/ginx/middlewares`, `app/api/api.ts` |
| Трассировка и телеметрия | `kit/infra/http.RouterOptions.TraceMiddleware` |
| RUM-провайдер | [`frontend/performance.md`](frontend/performance.md) |
| Production CDN и кеш | [`frontend/performance.md`](frontend/performance.md) |
| Численные performance-бюджеты | [`frontend/performance.md`](frontend/performance.md) |
| Продуктовые метрики | [`frontend/performance.md`](frontend/performance.md) |
| Кодогенератор контрактов | [`backend/nats-contracts.md`](backend/nats-contracts.md) |

## Инициализация завершена, когда

- [ ] идентичность заменена (`node scripts/init-project.mjs ...`);
- [ ] `node scripts/check-template-residue.mjs` не находит остатков;
- [ ] в `docs/decisions/ADOPTION.md` не осталось строк `pending`;
- [ ] `docs/PROJECT_MEMORY.md` создан заново и пуст;
- [ ] `docs/TEMPLATE_MEMORY.md` сохранён отдельно;
- [ ] судьба демо-доменов зафиксирована явно (оставлены или заменены);
- [ ] `pnpm install --frozen-lockfile` проходит;
- [ ] фронтенд: `build:local`, `lint`, `typecheck`, `test` зелёные;
- [ ] production-сборка приложения зелёная;
- [ ] бэкенд: `go build`, `go vet`, `go test` зелёные в обоих модулях;
- [ ] сгенерированные артефакты не закоммичены.

## Отметить репозиторий как GitHub Template

После того как процесс инициализации проверен на временной копии, владелец
репозитория может включить настройку **Template repository** в GitHub.

Это настройка репозитория, а не свойство исходного кода: подделать её в файлах
нельзя.

# Дополнительные проверки проекта

Этот документ сохраняется после `init-project`. Это готовые варианты развития,
а не включённые проверки. Обязательная база находится в [checks.md](checks.md),
причины выбора — в [ADR-0008](../decisions/0008-quality-checks.md).

При инициализации прочитайте таблицу и выберите подходящее проекту. Для выбранного
пункта зафиксируйте ADR, закрепите проверенную версию инструмента, добавьте
конфигурацию и самостоятельную команду. Включите команду в обязательный набор
проекта и его проверку инициализированной копии. Докажите PASS на исправном
случае и FAIL на представительном нарушении. Установка пакета сама по себе
не включает проверку; флагов выбора этих инструментов у `init-project` нет.

## Быстрый выбор

| Событие | Подключить | Цена |
|---|---|---|
| Началась собственная компонентная библиотека | Storybook Chromium smoke, затем browser behavior и a11y | Браузер, отдельное окружение тестов |
| Появились сложные цепочки фасадов, auto-imports или второй frontend | Анализ графа зависимостей и циклов | Resolver Vue/Nuxt, контроль generated metadata |
| Появились callback API с async-обработчиками | `no-misused-promises`, затем остальные typed rules | Дополнительные находки, уточнение TS projects |
| Рост мёртвых exports/зависимостей | Knip | Явные entrypoints Nuxt, stories и генераторов |
| Появились подавления анализаторов | Политика исключений и её фикстуры | Узкий scanner комментариев, учёт причины и владельца |
| Библиотеки публикуются или имеют второго потребителя | publint и consumer typecheck | Production-сборка и отдельный consumer |
| Меняется общий конкурентный Go-код | `go test -race ./...` | CGO/C-компилятор, больше памяти и времени |
| SQL генерируется, но запрос ломается на реальной схеме | sqlc vet + временный PostgreSQL | Миграции, подготовка БД |
| Proto получил второго потребителя | buf lint и breaking | Принятый baseline совместимости |
| Продукт готовится к публикации | govulncheck, Gitleaks, при необходимости Trivy | Свежие базы, отдельный внешний прогон |
| Повторяется конкретный дефект вне существующих анализаторов | Узкое Semgrep-правило | Поддержка правила и двух фикстур |
| Есть сомнение в ценности тестов критичного модуля | Выборочный StrykerJS/Gremlins | Долгий исследовательский прогон |

## TypeScript, импорты и архитектура

База уже включает `no-floating-promises` с `ignoreVoid: false`. Следующий
кандидат — `@typescript-eslint/no-misused-promises: error`. Добавьте его в
`packages/eslint-config/typed.js`, проверьте `pnpm lint` и негативный случай
с async-функцией в синхронном callback API. Проверьте TS и Vue, исходники и тесты.
Не заменяйте весь preset сразу: `recommendedTypeChecked`, затем
`strictTypeChecked` оцениваются отдельными изменениями. Кандидаты после promises:
`no-unsafe-assignment/call/return`, `no-unnecessary-type-assertion`,
`strict-boolean-expressions`, `no-unsafe-enum-comparison`.

ESLint content cache не доказывает корректность typed lint: измените возвращаемый
тип в импортируемом файле, оставив consumer неизменным, и убедитесь, что следующий
прогон всё равно обнаруживает ошибку. До такой проверки кеш не включается.

Базовое `workspace/boundaries` проверяет прямые imports, exports, literal dynamic
imports и import types, включая относительные переходы между пакетами. Оно не
строит транзитивный граф и не разрешает Nuxt auto-imports. Когда этого мало:

1. Добавьте `dependency-cruiser` в catalog/devDependencies frontend.
2. Создайте `.dependency-cruiser.cjs` с одной матрицей из `frontend/AGENTS.md`:
   библиотеки не зависят от приложений; API — от Vue; shared — от components;
   components — от API/роутера; запрещены циклы и приватные импорты.
3. Добавьте `lint:architecture`: `depcruise --config .dependency-cruiser.cjs packages applications`.
4. Настройте TypeScript aliases и Vue transpiler. Auto-imports требуют чтения
   актуальных метаданных Nuxt либо отдельного правила; отсутствие метаданных
   должно давать FAIL, а не пустой граф.
5. Замените дублирующие проверки границ, сохранив форматирование импортов в ESLint.
   Проверьте цикл, re-export обход, deep import и valid graph. Граф не пуст.

Стор пока использует классификацию отмены из `@starter/api/core`. Перенос этой
ответственности в адаптер — отдельное решение по ADR-0005/0007, не побочный
эффект ужесточения линтера (бывший QH-12).

Для Knip добавьте пакет в catalog, конфиг с реальными entrypoints и команду
`knip`. Негативная проба — заведомо неиспользуемый export/зависимость; положительная
— реально используемый auto-import или story. Не закрывайте находки широким ignore.

## Политика исключений

База уже запрещает `@ts-ignore`, требует описание у `@ts-expect-error` и
конкретное правило с объяснением у `//nolint`. Когда нужны дополнительные
гарантии (например, владелец и срок пересмотра исключения), добавьте
`check-quality-policy` как отдельную Node-команду. Проверяйте комментарии
`eslint-disable`, `@ts-expect-error`, `//nolint` и `#nosec` подходящим parser,
не принимая строковые литералы и generated/vendor за исключения кода.

Команда должна отклонять безымянное подавление всех правил, отсутствие причины,
неизвестное правило и просроченное исключение — в том объёме, который выбрал
проект. Для ESLint сначала используйте штатные `reportUnusedDisableDirectives`
и правила comment-плагина; отдельный scanner нужен для общей политики поверх
нескольких анализаторов, а не для повторения уже включённых проверок.
Добавьте команду в обязательный прогон вместе с её Node-фикстурами: допустимое
узкое исключение → PASS, широкое/просроченное → FAIL, похожая строка → PASS.

## Доступность и SCSS

ESLint a11y сейчас выдаёт предупреждения; обязательным барьером они не являются.
После исправления базовых интерактивных элементов можно перевести их в error
или запускать ESLint с `--max-warnings=0`. Проверяйте связанную label/input,
доступное имя, клавиатуру, фокус и пользовательский сценарий, а не только AST.

Для выполнения историй добавьте совместимые версии `@storybook/addon-vitest`,
`@vitest/browser-playwright` и `playwright`; addon включается в Storybook и
`storybookTest({ configDir })` — в отдельный Vitest browser project.
Установите Chromium через `playwright install chromium`. Команда истории:

```bash
node -e 'require("node:fs").mkdirSync("test-results", { recursive: true })'
storybook index --output-file test-results/story-index.json
vitest run --project stories-chromium
```

Проверяйте, что каждая story из индекса завершилась PASS: пустой индекс,
пропущенный проект, skipped/todo или исключённая обязательная история — FAIL.
Полезен отдельный reporter, сравнивающий прошедшие story IDs с полным индексом.
Негативная проба — throw в story или удаление обязательного случая из прогона.
Одна сборка Storybook не проверяет рендеринг. Задайте явный низкий порт browser
API (например, 6210), учитывая резервирование динамических портов Windows.

`@storybook/addon-a11y` добавляется отдельно. Для обязательной a11y-проверки
настройте режим, завершающий тест ошибкой при нарушении, и проверьте это на
контроле без доступного имени. Информационная панель Storybook не является гейтом.
Поведенческие тесты клавиатуры/фокуса/overflow запускайте в Chromium и WebKit.
Визуальные снимки вводите только вместе с утверждёнными эталонами и фиксированными
viewport, шрифтами, locale, timezone, темой и анимациями. Обновление снимков —
отдельное осознанное действие, а не способ сделать красный прогон зелёным.

Для стилей можно подключить Stylelint с SCSS/Vue parser и правилами проекта.
BEM-проверка должна требовать `block__element` и модификатор-атрибут: классы
`block--modifier` здесь противоречат ADR-0004. Правило из другого проекта,
допускающее такие классы, не переносится без адаптации. Не проверяйте SCSS
регулярным выражением, которое принимает комментарии и строки за селекторы.
Проверьте nesting, `:deep`, динамические классы и обычные CSS custom properties.

`max-lines: 1000` и запрет всего `void` не включены: первый ограничивает метрику,
второй дублирует лишь часть promise-политики. При принятии проектом их добавляют
явно, не ослабляя обработку ошибок ради прохождения линта.

## Библиотеки и генерация

Для publint добавьте проверенную версию в catalog и devDependencies библиотек.
Команда каждой библиотеки — `pnpm build && publint`. Проверяйте также импорт
JS и типов из отдельного consumer: базовый `check:packages` уже проверяет runtime
exports, относительные импорты и свежесть сборки. Негативная проба — публичный
export на отсутствующий файл либо несовместимые types/import условия.

Генерируемые SQL, protobuf, Swagger и realtime Go→TS/Zod проверяются через
повторную генерацию и отсутствие diff. Для межъязыкового сериализатора дополнительно
нужен golden round-trip на обеих сторонах. Реестр владельцев строится из реальных
контрактов: добавление нового владельца не должно оставлять его вне проверки.
Проверка должна отклонить изменённый generated-файл и пропущенного владельца.

## Go, SQL и protobuf

Базовый golangci-набор в `backend/.golangci.yml` расширяется по результатам
чистого прогона. Следующие кандидаты: `exhaustive`, `makezero`, `musttag`,
`testifylint`, `gocheckcompilerdirectives`, `forcetypeassert`, `errchkjson`,
`copyloopvar`, `gochecksumtype`, `spancheck`, `unqueryvet`.
Другие кандидаты из продуктового набора: `asasalint`, `canonicalheader`,
`decorder`, `errname`, `exptostd`, `fatcontext`, `gocritic`, `goprintffuncname`,
`iface`, `importas`, `maintidx`, `mirror`, `modernize`, `prealloc`, `predeclared`,
`misspell`, `nakedret`, `recvcheck`, `thelper`, `unconvert`, `usestdlibvars`,
`testableexamples`, `usetesting`, `wastedassign`, `whitespace`. Не все доступны
в закреплённой версии: сверяйте `golangci-lint linters`, совместимость с Go и
отрицательную пробу. `nilnil`, `protogetter` и NilAway — отдельные кандидаты,
а не унаследованные обязательные правила. `enable-all` не используется.

Полная проверка конкурентности из каждого модуля:

```bash
go test -race ./...
```

Нужны поддерживаемая платформа и CGO/C-компилятор. Включайте в обязательный
полный прогон при работе с cache/runtime/ratelimiter; падение из-за отсутствия
компилятора не считается прохождением. Негативная проба для wiring — известная
гонка в изолированном временном модуле, никогда в рабочем приложении.

`sqlc vet -f sqlc/sqlc.yaml` подключается с осмысленными `rules` конфигурации,
а для проверки реальной схемы — `sqlc/db-prepare` и временной PostgreSQL после
миграций. Без правил команда не доказывает требуемый инвариант. Негативная проба —
конкретный запрещённый запрос или несовпадение со схемой.

Для proto создайте `buf.yaml` с выбранной lint-политикой и запустите `buf lint`.
Генерация остаётся существующей. Совместимость:

```bash
buf breaking --against <approved-baseline>
```

Baseline выбирает проект: tag, commit либо registry. Проверьте удаление поля
и несовместимую смену типа. Наличие proto без второго потребителя не требует
самостоятельной инфраструктуры версионирования контрактов.

## Инфраструктура и безопасность

Штатные дешёвые проверки инфраструктуры (если менялись соответствующие файлы):

```bash
bash -n scripts/dev.sh
docker compose --parallel 8 -f docker-compose.yml config --quiet
docker build --check -f docker/Dockerfile.service --build-arg SERVICE_DIR=gotemplate .
docker build --check -f docker/Dockerfile.frontend .
```

Каждый shell-файл передавайте `bash -n` отдельным вызовом; дополнительные
аргументы после имени скрипта не означают проверку второго файла. Compose
проверяйте со всеми реально поддерживаемыми overlays/profiles и необходимыми
переменными окружения. Эти команды проверяют конфигурацию, не runtime контейнера.
Hadolint добавляйте для конкретных дополнительных правил Dockerfile, сохраняя
штатные build checks; широкие ignore не нужны.

Внешние security-проверки не определяют базовую локальную корректность:

| Инструмент | Команда после установки закреплённой версии | Негативная проба / условие |
|---|---|---|
| govulncheck | `govulncheck ./...` из каждого Go-модуля | Тестовый модуль с известной уязвимой вызываемой функцией; свежая база |
| Gitleaks | `gitleaks dir .` для дерева; `gitleaks git .` для истории | Синтетический секрет из тестового корпуса, не реальный токен |
| Trivy | `trivy fs --exit-code 1 --severity HIGH,CRITICAL .` | Согласовать scanners и severities; база и сеть |
| Semgrep | `semgrep scan --config <project-rules> --error` | PASS/FAIL фикстуры для каждого собственного правила |

`gosec` уже входит в golangci-lint, второй запуск не нужен. Историю секретов и
сканирование образов держите вне быстрого локального цикла. Настройка реального
секрета для теста запрещена. Публичный репозиторий тестовых уязвимостей не
становится dependency приложения.

## Качество тестов и отчёты

Coverage-порог принимается по значимым веткам и честному знаменателю, без
произвольного универсального процента. Нельзя улучшать цифру исключением
непокрытого production-кода. `playwright test --list` проверяет только discovery,
а не работу селекторов и сценариев; для E2E требуется выполнение тестов.

StrykerJS с Vitest и Gremlins для Go подходят для выборочного исследования
критичной логики. Ограничьте список файлов, разберите выжившие мутации; не
добавляйте обязательный общий mutation score, CSS/generated/Storybook-обвязку
и регулярный полный прогон без решения, которое зависит от результата.

Если появился потребитель отчётов, договоритесь о `artifacts/quality/` и
форматах LCOV/Go cover/JSON/SARIF. Добавьте каталог в ignore и проверку, что
ожидаемый отчёт создан, не пуст и содержит нужные исходники. Отсутствующий
отчёт должен делать команду красной. Без потребителя не нужен агрегатор.

Новые анализаторы, их версии, исключения и команды должны переживать
переименование проекта. Повторите проверку инициализированной копии и
положительную/отрицательную пробу после замены идентичности.

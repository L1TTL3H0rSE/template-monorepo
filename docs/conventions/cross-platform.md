# Windows, Linux и воспроизводимость

Класс ошибок, где «у меня работает» верно буквально: на разных машинах разный
результат при одинаковом коде.

## Регистр в именах файлов

| Система | Поведение |
|---|---|
| Linux (ext4) | `Icons.vue` и `icons.vue` — два разных файла |
| Windows (NTFS) | один файл |
| macOS (APFS по умолчанию) | один файл |

Git при этом хранит **путь как строку** и видит два файла.

### Как это стреляет

Кодогенератор на машине разработчика создаёт `Icons.stories.ts`, в CI —
`icons.stories.ts`. Оба попадают в индекс Git. На Windows файловая система
отдаёт один файл на оба пути: `git status` показывает вечное изменение, которое
нельзя ни закоммитить, ни откатить. Submodule навсегда остаётся dirty.

### Правило

Один канонический регистр, проверяемый автоматически:

```js
function assertNoCaseCollisions(names) {
  const seen = new Map();
  for (const name of names) {
    const key = name.toLowerCase();
    if (seen.has(key)) {
      throw new Error(`"${seen.get(key)}" и "${name}" различаются только регистром`);
    }
    seen.set(key, name);
  }
}
```

Проверка в генераторе, а не в ревью: заметить `Icons.vue` рядом с `icons.vue` в
списке из полусотни файлов глазами не получается.

Дополнительно имена компонентов проверяются на PascalCase — идентификатор
экспорта регистрозависим всегда, в отличие от имени файла.

## Порядок вывода генератора

Два источника недетерминизма, оба реальные:

**1. `fs.readdir` не гарантирует порядок.** Он зависит от файловой системы и
порядка создания файлов.

**2. `Array.prototype.sort()` без компаратора** сравнивает строки по кодовым
единицам UTF-16, а `localeCompare()` без явной локали — по локали машины.
Кириллица, диакритика и регистр сортируются по-разному на разных хостах.

### Правило

```js
.sort((a, b) => a.localeCompare(b, "en"))
```

Локаль указывается **явно**. Для числовых значений сортировка идёт по значению,
и только при равенстве — по имени:

```js
Object.entries(breakpoints).sort(
  ([nameA, valueA], [nameB, valueB]) =>
    valueA - valueB || nameA.localeCompare(nameB, "en"),
);
```

Дополнительно это означает, что **перестановка строк в источнике не меняет
сгенерированный файл** — иначе каждый merge даёт конфликт в артефакте.

### Проверка

Генератор детерминирован, если повторный запуск не меняет рабочее дерево:

```bash
pnpm --filter @roleplay/components generate
git status --short   # пусто
```

Эту же проверку стоит держать в CI: она ловит недетерминизм до того, как он
дойдёт до чужой машины.

## Концы строк

`.gitattributes` фиксирует `* text=auto eol=lf`.

Без этого Windows коммитит CRLF, и shell-скрипты в Linux-контейнерах падают с
`bad interpreter: /bin/sh^M` — сообщение, по которому причина не угадывается.

## Разделители пути

В генераторах и скриптах — только `node:path`:

```js
resolve(here, "../src/components")   // ✔
here + "/../src/components"          // ✘ ломается на Windows
```

В путях внутри исходников (`import`, `@/`) — всегда прямой слэш: это URL-
подобные спецификаторы, а не пути файловой системы.

## Права на артефакты в Docker

Bind-mount каталога, который создан root'ом внутри контейнера, делает его
недоступным для локального пользователя: `pnpm build` падает с `EACCES`, и
удалить каталог можно только через `sudo`.

Два правила:

1. `dist`, `.nuxt`, `.output`, `node_modules` — в `.dockerignore`. Артефакты
   создаются ровно в одном месте: либо на хосте, либо в образе.
2. Финальный образ работает от непривилегированного пользователя (`USER app`).

## Чек-лист скрипта-генератора

- [ ] Сортировка с явной локалью `"en"`.
- [ ] Порядок не зависит от `fs.readdir`.
- [ ] Проверка на коллизии по регистру.
- [ ] Пути через `node:path`.
- [ ] Повторный запуск не меняет рабочее дерево.
- [ ] В файле есть пометка «сгенерировано, не редактировать вручную».

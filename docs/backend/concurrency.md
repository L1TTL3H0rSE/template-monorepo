# Фоновые задачи и гонки записи

Документ про класс ошибок, которые не воспроизводятся локально и не ловятся
тестами: два процесса записывают одно и то же поле.

## Две реплики одного воркера

Фоновая задача почти всегда выполняется больше чем в одном экземпляре, даже
если в конфигурации указан один:

- сервис поднят в нескольких репликах;
- во время rolling update старая и новая версия работают одновременно;
- разработчик запустил ручной прогон рядом с автоматическим.

Без взаимного исключения оба экземпляра выбирают «просроченные» записи одним и
тем же запросом и обрабатывают их дважды.

### Решение: advisory lock

```go
acquired, err := pglock.TryWithinTx(ctx, pool, "characters:reconcile",
    func(ctx context.Context, tx pgx.Tx) error {
        return reconcile(ctx, query.New(tx))
    })
if err != nil {
    return err
}
if !acquired {
    // Не ошибка: выполняет соседняя реплика. Пропускаем тик.
    return nil
}
```

Четыре решения внутри `kit/pglock`, каждое из которых стоило бы отдельного
инцидента:

| Решение | Альтернатива и её цена |
|---|---|
| `pg_try_advisory_xact_lock` | Сессионный `pg_advisory_lock` требует явного unlock; забытый unlock блокирует задачу до перезапуска сервиса |
| Транзакционная область | Блокировка снимается и при commit, и при rollback, и при падении процесса |
| `try`, а не блокирующий вариант | Блокирующий копит очередь воркеров, которые проснутся все разом |
| Имя вместо числа | `pg_advisory_lock(42)` однажды переиспользуют для другой задачи; хеш от имени исключает коллизию |

Отдельная таблица блокировок и внешний координатор не нужны: блокировка живёт в
той же БД, которой сервис уже владеет.

## Внешнее событие против фонового сверщика

Классическая пара: приходит вебхук со статусом, и параллельно крон сверяет
состояние с внешней системой. Оба обновляют одну строку.

```text
t0  вебхук читает строку
t1  сверщик читает ту же строку
t2  вебхук пишет status=finished, finished_at=12:00
t3  сверщик пишет status=finished, finished_at=NULL   <- затёр
```

Порядок записи определяется случайностью планировщика, поэтому ошибка
воспроизводится «иногда».

### Правило 1: не перезаписывать заполненное

```sql
-- name: MarkFinished :exec
UPDATE session
SET status      = 'finished',
    -- COALESCE: запоздалый источник не затирает уже известное время.
    finished_at = COALESCE(session.finished_at, sqlc.arg('finished_at')),
    updated_at  = now()
WHERE id = sqlc.arg('id');
```

`COALESCE(существующее, новое)` означает «заполнить, если пусто». Первое
достоверное значение выигрывает, а не последнее записанное.

### Правило 2: не откатывать статус назад

```sql
WHERE id = sqlc.arg('id')
  -- Терминальное состояние не возвращается в промежуточное: запоздалый
  -- вебхук «in_progress» не должен воскрешать завершённую сессию.
  AND status <> 'finished'
```

Условие в `WHERE`, а не `if` в Go: между чтением и записью в Go проходит время,
в течение которого состояние меняет кто-то ещё.

### Правило 3: писать под блокировкой строки, если нужен read-modify-write

```sql
SELECT ... FROM session WHERE id = $1 FOR UPDATE;
```

Нужен, когда новое значение вычисляется из старого (счётчики, накопление). Для
«заполнить, если пусто» достаточно `COALESCE`.

## Идемпотентность обработчика

Внешняя система доставляет событие **минимум один раз**, а не ровно один.
Повторная доставка обязана быть безопасной.

Дешёвый способ — уникальный ключ события:

```sql
CREATE TABLE processed_event (
    id          text PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);
```

```sql
-- name: ClaimEvent :one
INSERT INTO processed_event (id)
VALUES ($1)
ON CONFLICT DO NOTHING
RETURNING id;
```

Пустой результат означает «уже обработано» — обработчик выходит, возвращая
успех. Возврат ошибки заставил бы внешнюю систему повторять доставку вечно.

## Чек-лист фоновой задачи

- [ ] Взаимное исключение через `pglock.TryWithinTx`.
- [ ] «Блокировку держит другой» — не ошибка, а пропуск тика.
- [ ] Обновление статуса не откатывает терминальное состояние.
- [ ] Заполнение времени и внешних идентификаторов — через `COALESCE`.
- [ ] Повторная доставка события безопасна.
- [ ] Тик ограничен по количеству записей: неограниченная выборка на
      накопившемся долге выедает память и держит транзакцию открытой.

# Засев корневых данных

## Проблема: циклическая зависимость прав

Как только доступ считается по данным (кто ты, где ты числишься, что тебе
назначено), развёртывание «с нуля» упирается в цикл:

```text
чтобы выдать роль администратора  -> нужен пользователь
чтобы создать пользователя        -> нужно подразделение
чтобы создать подразделение       -> нужны права администратора
```

Через публичный API цикл не разрывается **в принципе**: каждая точка входа
проверяет доступ, а решать некому — субъекта ещё нет.

Симптом: стенд поднимается только копированием дампа БД с чужой машины. Через
месяц никто не знает, что в этом дампе и почему.

## Решение: one-shot команда внутри владельца

```text
backend/gotemplate/cmd/bootstrap/main.go     точка входа
backend/gotemplate/internal/app/bootstrap.go засев
```

```bash
go run ./cmd/bootstrap
```

Четыре обязательных свойства:

### 1. Внутри сервиса-владельца

Команда пишет **только в свою** схему, напрямую через слой хранилища. Отдельный
сервис-сеятель, который ходит в чужие базы, восстанавливает ровно ту связность,
которую разделение сервисов убирало.

### 2. В обход HTTP и проверки доступа

Это единственное, что разрывает цикл. Одновременно это причина, по которой
команда не может быть HTTP-эндпоинтом: эндпоинт, создающий администратора без
проверки прав, — открытая дверь, даже «временная».

### 3. Идемпотентность

Команда запускается при каждом подъёме стенда и в CI. Повторный запуск не
создаёт дубликатов и не падает:

```go
existing, err := q.CountExamplesByName(ctx, name)
if existing > 0 {
    continue
}
```

Проверка и вставка выполняются в **одной транзакции под блокировкой** — иначе
два параллельных запуска оба увидят пустую выборку и оба вставят.

### 4. Завершаемость

Команда выходит с кодом 0 при успехе и ненулевым при ошибке. В compose она
подключается как init-контейнер:

```yaml
gotemplate:
  depends_on:
    gotemplate-bootstrap:
      # Не service_started: сервис не должен подниматься на наполовину
      # заполненной БД, иначе причина отказа обнаружится далеко от места.
      condition: service_completed_successfully
```

## Что засевается, а что нет

| Засевается | Не засевается |
|---|---|
| Корневая роль и её назначение | Демонстрационные персонажи для скриншотов |
| Системное подразделение | Тестовые пользователи под нагрузку |
| Служебная учётная запись интеграции | Данные для конкретного QA-сценария |
| Справочник, на который ссылается схема | Всё, что нужно одному разработчику |

Критерий: **без этой записи система неработоспособна**. Всё остальное — фикстуры,
и они живут отдельно, чтобы никогда не попасть в production.

Смешение этих двух наборов — самая частая ошибка: сначала в засев добавляют
«одного тестового пользователя для удобства», потом он оказывается в проде с
известным паролем.

## Взаимное исключение

```go
acquired, err := pglock.TryWithinTx(ctx, pg.Pool(), "gotemplate:bootstrap", seed)
if !acquired {
    log.Info("bootstrap skipped: lock held by another instance")
    return nil   // код возврата 0
}
```

Пропуск засева соседней репликой — **не ошибка**. Возврат ненулевого кода здесь
уронил бы подъём стенда на гонке, которой нет.

Подробнее о блокировках — [`concurrency.md`](concurrency.md).

## Добавление засева в новый сервис

1. Скопировать `cmd/bootstrap` и `internal/app/bootstrap.go`.
2. Заменить `seedNames` на свои корневые данные.
3. Добавить сервис `<имя>-bootstrap` в `docker-compose.yml`.
4. Прописать `condition: service_completed_successfully` в зависимостях
   сервиса.
5. Проверить идемпотентность: запустить дважды подряд, второй запуск обязан
   завершиться без изменений.

Шаг 5 не пропускается — именно он ловит забытую проверку «уже есть».

# Схема, запросы и sqlc

## Цикл изменения

```bash
# 1. новая пара файлов миграции
go run github.com/magefile/mage database:create add_character_status

# 2. запрос в internal/query/*.sql

# 3. генерация
go run github.com/magefile/mage generate:sqlc

# 4. сценарий, хендлер, маршрут
go build ./... && go test ./...
```

## Миграции

- Каталог `migrations/` внутри сервиса. Схемой владеет сервис; чужие таблицы он
  не мигрирует и не читает.
- Каждая миграция — пара `NNNNNN_name.up.sql` / `.down.sql`.
- **Применённая миграция не переписывается.** Изменение схемы всегда добавляет
  следующую пару.

Причина последнего правила: миграция, применённая на любом стенде, уже
зафиксирована в таблице версий. Правка её содержимого не выполнится повторно —
схема стендов разойдётся молча, и расхождение обнаружится при следующем
несовместимом запросе.

Миграции применяются при старте (`pg.RunMigrations`). Это нормально для одного
экземпляра сервиса; при нескольких репликах вынесите шаг в отдельную задачу
деплоя.

## sqlc: почему он

Альтернативы и их цена:

| Подход | Цена |
|---|---|
| ORM | Скрывает генерируемый SQL; оптимизировать запрос можно только через обход ORM |
| Рукописные `Scan` | Добавление колонки требует правки каждого места; ошибка порядка полей — рантайм |
| sqlc | SQL пишется явно, а Go-код и типы генерируются из него |

`sqlc` даёт третье свойство, которого нет у первых двух: несоответствие запроса
и схемы падает **на генерации**, а не в проде.

## `emit_interface: true`

Обязателен. Он порождает `query.Querier` — интерфейс, который:

- служит тестовым швом (фейк без БД — см. [`testing.md`](testing.md));
- избавляет от рукописного `store`-интерфейса поверх сгенерированного кода.

Без него единственный способ протестировать сервис — поднимать БД.

## Три ловушки sqlc

### 1. Override по внутреннему имени типа Postgres

sqlc сопоставляет `overrides` по **внутреннему** имени типа, а не по алиасу.
Для nullable-параметров запись `db_type: "bigint"` не применяется:

```yaml
- db_type: "pg_catalog.int8"    # именно так, а не "bigint"
  nullable: true
  go_type:
    type: "int64"
    pointer: true
```

Без этих строк nullable-поля остаются `pgtype.Int8`, и сервис пишет ручные
конвертеры `pgtype ↔ указатель` — ровно то, ради устранения чего sqlc и
внедряли. Нужны три записи: `pg_catalog.int8`, `pg_catalog.int4`,
`pg_catalog.bool`.

### 2. Порядок колонок должен совпадать со схемой

sqlc переиспользует общий тип таблицы (`query.Example`) только при **полном**
совпадении формы выборки со схемой. Иначе он выдаёт отдельный `<Query>Row` на
каждый запрос:

```sql
-- Совпадает со схемой -> тип query.Example, один маппер на весь сервис
SELECT id, name, created_at FROM example WHERE id = $1;

-- Не совпадает -> тип GetExampleRow, нужен ещё один маппер
SELECT name, id, created_at FROM example WHERE id = $1;
```

Практическое следствие: колонка из поздней миграции стоит в таблице последней —
значит, и в `SELECT`/`RETURNING` тоже.

Проверить легко: `internal/query/models.go` должен содержать один тип на
таблицу, а `example.sql.go` — не порождать `...Row`-структуры для запросов той
же формы.

### 3. Один параметр в двух ролях — ошибка 42P08

Позиционный параметр, использованный и как значение колонки, и внутри
выражения, оставляет Postgres без однозначного типа:

```sql
-- Падает: 42P08 could not determine data type of parameter $2
INSERT INTO session (id, status, retry_count)
VALUES ($1, $2, CASE WHEN $2 = 'failed' THEN 1 ELSE 0 END);
```

Postgres выводит тип параметра из контекста. В `VALUES` контекст — тип колонки,
внутри `CASE` — результат сравнения; два разных вывода для одного `$2`
несовместимы.

Лечится явным приведением в **каждом** использовании:

```sql
INSERT INTO session (id, status, retry_count)
VALUES (
    sqlc.arg('id'),
    sqlc.arg('status')::text,
    CASE WHEN sqlc.arg('status')::text = 'failed' THEN 1 ELSE 0 END
);
```

Ошибка возникает **в рантайме при подготовке запроса**, а не на `sqlc generate`:
генератор выводит типы своим анализатором и такой запрос пропускает. Поэтому
запросы с параметром в двух ролях обязательно прогоняются против реальной БД.

### 4. Агрегату и выражению нужен явный тип

```sql
-- Без cast sqlc не выводит тип и отдаёт interface{}
SELECT COUNT(*)::bigint AS total FROM example;
SELECT COALESCE(BOOL_OR(is_active), FALSE)::boolean AS any_active FROM example;
```

## Именованные параметры

Позиционные `$1` дают сгенерированные имена вида `dollar_1`:

```go
CountExamples(ctx context.Context, dollar_1 string) (int64, error)
```

`sqlc.arg` / `sqlc.narg` дают осмысленные:

```sql
LIMIT sqlc.arg('page_size') OFFSET sqlc.arg('page_offset')
WHERE (sqlc.narg('search')::text IS NULL OR name ILIKE '%' || sqlc.narg('search')::text || '%')
```

```go
ListExamples(ctx context.Context, arg ListExamplesParams) ([]Example, error)
// ListExamplesParams{ Search *string; PageOffset int; PageSize int }
```

`narg` — nullable-параметр: он даёт `*string`, и «фильтр не задан» отличается
от «фильтр пустой».

## Комментарии в `.sql`

Комментарий непосредственно над `-- name: ...` попадает в doc-комментарий
сгенерированного метода и в интерфейс `Querier`. Пояснения для разработчика
пишите либо в этом файле-документе, либо после строки `-- name:`.

## Генерируемые файлы

`internal/query/db.go`, `models.go`, `querier.go`, `*.sql.go` содержат
`Code generated by sqlc. DO NOT EDIT.`

Они **коммитятся** — чтобы сборка не требовала генератора, — но правятся только
через `.sql` и `sqlc generate`. Правка «на месте» потеряется при следующей
генерации, и никакой ошибки при этом не будет.

## Пагинация и фильтрация

Остаются в SQL. Загрузить весь набор и отфильтровать в Go — решение, которое
работает на тестовых данных и ложится на реальных.

`total` считается отдельным запросом `COUNT(*)` по тому же условию: длина
страницы не равна общему количеству.

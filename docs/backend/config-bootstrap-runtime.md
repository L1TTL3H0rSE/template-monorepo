# Конфигурация, composition root и жизненный цикл

## Конфигурация

Единственный источник — переменные окружения. `.env` подхватывается только для
локальной разработки и **не коммитится**; в контейнере значения приходят из
compose или секретов.

```go
type Config struct {
    bootstrap.Common                          // LOG_*, CACHE_*, RATELIMIT_*

    Server   kithttp.Config  `env-prefix:"SERVER_"`
    Database postgres.Config `env-prefix:"DB_"`
}
```

Имя переменной **выводится из структуры**: префикс блока + имя поля.
`Database.Host` → `DB_HOST`, `Server.ReadTimeout` → `SERVER_READ_TIMEOUT`.
Отдельной таблицы соответствий не существует, поэтому она не может устареть.

Значения по умолчанию живут в теге рядом с полем:

```go
Port int `env:"PORT" env-default:"8080"`
```

### Чего тег не выражает

`env-required` отвечает на вопрос «переменная есть?», а не «значение
осмысленно?»: `DB_NAME=""` он пропускает. Там, где инвариант сформулирован по
значению, он живёт в методе рядом с блоком конфигурации:

```go
func (c *Config) Validate() error
```

`postgres.Config.Validate` отвергает пустое и пробельное имя базы и вызывается
из `Adapter.Connect`, то есть до любого сетевого действия. Умолчания хоста,
порта и пользователя при этом остаются: недоступный хост виден сразу, а имя
базы по умолчанию тихо увело бы записи в служебную `postgres`.

### `.env.example` обязателен

Он перечисляет **все** переменные с их блоками. Это единственная документация
внешних зависимостей сервиса, и её нельзя забыть обновить: новое поле в
структуре без строки в примере — незаметный отказ при деплое.

### Порядок приоритетов

1. Переменные окружения процесса.
2. `.env`, если файл есть.

`godotenv.Load` не перезаписывает уже установленные переменные — окружение
контейнера всегда сильнее локального файла.

## Composition root

`internal/app/app.go` — **единственное** место, где создаются зависимости.

```go
func Run(ctx context.Context) error {
    cfg, err := config.Load()                                  // 1. конфигурация
    foundations, err := bootstrap.Init(ctx, "gotemplate", cfg.Common)  // 2. общее
    log := foundations.Zap()

    pg := postgres.NewAdapter(&cfg.Database, log)              // 3. ресурсы
    pg.Connect(ctx)
    pg.RunMigrations(ctx, "migrations")

    exampleService := examplesvc.New(query.New(pg.Pool()), log)  // 4. домен

    httpServer := httpinfra.NewServer(&cfg.Server, httpinfra.Deps{  // 5. транспорт
        Logger:      log,
        RateLimiter: foundations.RateLimiter,
        Example:     exampleService,
    })

    rt := runtime.New(runtime.WithLogger(log))                 // 6. жизненный цикл
    rt.Add(runtime.InfraComponent("http", httpServer))
    foundations.RegisterClosers(rt)
    rt.AddCloser(runtime.CloserFunc("postgres", func(context.Context) error {
        pg.Close()
        return nil
    }))

    return rt.Run(ctx)
}
```

Ни один другой пакет не вызывает конструкторы соседних слоёв: хендлер не
создаёт сервис, сервис не открывает соединение с БД. Благодаря этому весь граф
зависимостей читается на одном экране.

**Почему не DI-контейнер:** контейнер переносит ошибки связывания из compile-time
в runtime и делает граф невидимым. Явная функция даёт ту же развязку, ловится
компилятором и читается без документации.

## Общие примитивы: `bootstrap`

`bootstrap.Init` строит логгер, кеш и rate limiter из одного встроенного блока
конфигурации. Это заменяет ~40 строк одинаковой обвязки, которые иначе
копируются в `app.go` каждого сервиса — и расходятся.

Новый общий примитив добавляется в `bootstrap`, а не в отдельный сервис.

## Жизненный цикл: `runtime`

`runtime.Runtime` владеет:

- **Component** — долгоживущая единица (HTTP-сервер, потребитель очереди).
  Стартуют в порядке регистрации, останавливаются в обратном.
- **Closer** — ресурс только на закрытие (пул БД, соединение с брокером).
  Закрываются в обратном порядке **после** остановки всех компонентов.

```text
старт:      логгер -> БД -> сервисы -> HTTP
остановка:  HTTP -> сервисы -> БД -> логгер
```

### Почему порядок обратный

Если закрыть пул БД раньше, чем остановлен HTTP-сервер, запрос в полёте упадёт
на закрытом соединении. Обратный порядок гарантирует, что ресурс жив, пока жив
его потребитель.

Отсюда правило регистрации в `app.go`:

```go
foundations.RegisterClosers(rt)   // общие closers — первыми
rt.AddCloser(...)                 // ресурсы сервиса — после
```

При обратном закрытии пул БД уходит раньше логгера, и последняя запись об
остановке всё ещё попадает в лог.

### Fail-fast

Ошибка `Start` любого компонента отменяет контекст и роняет весь `Runtime`.
Сервис, который поднялся наполовину, хуже упавшего: он проходит health-check и
принимает трафик, который не может обслужить.

### Graceful shutdown

`Run` блокируется до отмены контекста (SIGINT/SIGTERM) или первой ошибки, затем
останавливает всё в обратном порядке с общим таймаутом (по умолчанию 30 с) и
агрегирует ошибки через `errors.Join`.

Агрегация, а не первая ошибка: при остановке важно увидеть **все** проблемы —
вторая часто объясняет первую.

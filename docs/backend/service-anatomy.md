# Анатомия Go-сервиса

Эталон — [`backend/gotemplate`](../../backend/gotemplate). Новый сервис
начинается с копии этого каталога.

`gotemplate` — не «пример для чтения», а **исполняемое определение паттерна**.
Общий приём меняется здесь, и остальные сервисы подтягиваются к новой форме.
Доменная особенность одного сервиса в шаблон не вносится.

## Каталоги

```text
cmd/app/main.go                entrypoint: сигналы ОС -> app.Run
config/config.go               Common + доменные блоки конфигурации
internal/app/app.go            composition root и жизненный цикл
internal/domain/dtos/          Input / Patch / View — единственный слой форм
internal/infra/http/           сервер, роутер
internal/infra/http/controllers/  транспорт: разбор запроса и форма ответа
internal/infra/services/       сценарии
internal/query/                *.sql + сгенерированный sqlc-код
migrations/                    схема, которой владеет сервис
pkg/permissions/               публичный каталог разрешений владельца
proto/                         source of truth межсервисных контрактов
sqlc/sqlc.yaml                 конфигурация генератора
magefile.go                    канонические команды
.env.example                   полный список переменных с их блоками
```

## Что означает `internal/` и `pkg/`

Это не стилистика — Go применяет `internal/` на уровне компилятора.

| Каталог | Кто может импортировать | Что туда кладут |
|---|---|---|
| `internal/` | только этот модуль | всё, что не является контрактом |
| `pkg/` | любой сервис | контракты, на которые опираются другие |

Правило: **по умолчанию код идёт в `internal/`.** Переезд в `pkg/` — осознанное
решение опубликовать контракт и дальше поддерживать его совместимость.

## Порядок чтения незнакомого сервиса

1. `README.md` — что за сервис.
2. `internal/app/app.go` — что он поднимает и в каком порядке. Это самый
   информативный файл: composition root показывает все зависимости разом.
3. `internal/infra/http/router.go` — вся поверхность HTTP на одном экране.
4. `migrations/` — какими данными он владеет.
5. `config/config.go` + `.env.example` — от чего он зависит снаружи.

Пятью файлами покрывается сервис любого размера, потому что каждый из них
единственный в своей роли.

## Независимость модулей

Каждый `backend/<module>` — самостоятельный Go-модуль. Общего `go.work нет`.

```bash
cd backend/gotemplate
go build ./...
go vet ./...
go test ./...
```

Соседние модули подключаются через `replace`:

```go
require roleplay/kit v0.0.0

replace roleplay/kit => ../kit
```

**Почему так, а не единый модуль или `go.work`:** общий workspace делает сборку
одного сервиса зависимой от компилируемости всех остальных. Здесь сломанный
сосед не мешает работать, а локальный цикл разработки остаётся мгновенным.

## Создание нового сервиса

1. Скопировать `backend/gotemplate` в `backend/go<domain>`.
2. Заменить `module roleplay/gotemplate` в `go.mod` и все импорты.
3. Переименовать домен `example` в свой.
4. Заменить `migrations/000001_initial_schema.*` на свою схему.
5. Обновить `pkg/permissions/permissions.go`: `ServiceCode`, actions, ресурсы.
6. Добавить сервис в корневой `docker-compose.yml`.
7. Прогнать `go build ./... && go vet ./... && go test ./...`.

Шаг 7 обязателен до первой доменной строки: он подтверждает, что копия
самостоятельна.

## Что нельзя делать между сервисами

| Запрещено | Почему |
|---|---|
| Импорт `internal/` соседа | Компилятор запретит; попытка обойти — признак неверной границы |
| Чтение таблиц соседа | Владелец не сможет менять свою схему, не сломав чужой сервис |
| Внешний ключ в чужую БД | Связывает жизненные циклы и делает независимый деплой невозможным |
| Копия subject/типа сообщения соседа | Переименование у владельца молча разойдётся с копией |

Междоменная ссылка хранится как идентификатор, а её валидность проверяется
через публичный контракт владельца.
